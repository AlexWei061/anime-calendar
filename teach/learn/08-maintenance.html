LESSON 08约 55 分钟需求 · TDD · 验证

“修好了”
是一条待证明命题

工程能力不是一次写对，而是建立一套让错误容易暴露、改动范围容易审查、结论有证据支持的流程。

THE LOOP

八步安全修改闭环

  1. 定义成功标准把“更好看”“有问题”改写成可观察行为。
  2. 定位责任层沿项目地图找第一个错误层，不先猜文件。
  3. 最小复现找到稳定输入，让问题可重复出现。
  4. 写回归测试把反例转为自动断言，并亲眼看它因目标问题失败。
  5. 做最小修复只改变足以让测试通过的规则或数据。
  6. 跑针对测试确认新反例变绿，附近行为没有退化。
  7. 跑完整验证lint、npm test、git diff --check。
  8. 审查范围再交付diff 只含任务文件；提交、推送、部署是三个独立授权。
证据不变量没有刚刚运行的命令输出，就不能声称测试通过；没有能失败的回归测试，就不能证明测试捕获了原 bug。

CLARIFY

把模糊需求改写成判定条件

模糊
凌晨节目显示不对，修一下。
可验证
周四 04:59 的节目显示在周三栏，
标签为“次日 04:59”；周四 05:00
仍显示在周四栏。桌面、移动端一致。

第二种写法直接给出两个边界样例、期望输出和受影响界面。它已经非常接近回归测试。

像数学命题必须写清定义域、量词和结论。需求越模糊，越无法判断一个实现是否真的满足它。

RED

复现与回归测试：先看到红

修 bug 时，先在最接近规则的测试文件中增加一个最小反例。测试必须因目标缺陷失败，而不是因为路径写错、语法错误或环境没装好。

test("keeps the calendar on the previous broadcast day until 05:00", () => {
  assert.equal(
    calendarDateForDateTime("2026-08-27", "04:59"),
    "2026-08-26",
  );
  assert.equal(
    calendarDateForDateTime("2026-08-27", "05:00"),
    "2026-08-27",
  );
});
红灯检查
失败原因
实际输出与期望日期不同。
不是环境错
测试文件能正常加载，其他样例仍运行。
足够小
只证明一个阈值，不同时测试整页样式。
用户可见
对应节目最终出现在哪一天。

GREEN

最小修复：只改变命题需要的部分

若根因是共享日期阈值，就修 layoutBroadcast；不要同时重写日期库、移动 JSX、格式化大文件或升级依赖。

好修复

改一个阈值或分支，复用现有函数，新增边界测试。

危险修复

在 CSS、桌面 JSX 和移动 JSX 分别加补丁，产生三份日期规则。

好数据修复

先确认来源，再按生成流程重建目录和图集。

危险数据修复

手改生成文件，下次运行脚本后修复消失。

范围不变量只修改当前成功标准需要的代码；无关问题可以记录，但不顺手修复。

VERIFY

不同证据证明不同结论

命令能证明不能单独证明
针对测试报告的反例和附近行为全仓库无回归
npm run lint -- --ignore-pattern .worktrees规则检查通过构建与业务行为
npm test类型、生产构建、全部现有测试未被测试覆盖的视觉细节
git diff --check无空白错误和冲突标记逻辑正确
git diff --stat改动规模是否异常每一行都必要
node --test --test-name-pattern="报告症状" tests/相关文件.test.mjs
npm run lint -- --ignore-pattern .worktrees
npm test
git diff --check
git status --short

PROOF TEMPLATE

用五句话交付一次修复

命题：报告的 bug 已修复。
修复前反例：新增回归测试在报告输入上失败。
构造：只修改负责该规则的最小代码或数据。
修复后证据：回归测试、相关测试、lint、npm test 通过。
范围证明：git diff 只包含本任务相关文件。

如果其中一句写不出来，说明证据链仍有缺口。尤其不要把“代码看起来对”替代为“测试实际通过”。

这就是构造性证明：给出反例、构造修复，再验证新对象满足约束，并证明没有越出定义域。

STOP CONDITIONS

什么时候必须停下来确认

  • 需求有两种解释，会导致不同数据模型或交互；
  • 需要删除、覆盖、迁移真实数据或改变访问权限；
  • 需要推送、部署、发消息或调用外部服务；
  • 发现工作区已有改动与当前任务重叠；
  • 测试基线原本就失败，无法区分新旧问题；
  • 同一个验证错误重复出现，计划中的假设可能错误。
授权不变量“完成实现”不自动等于获准推送或部署；外部状态变化需要明确授权。

CHECK YOUR MODEL

小测：测试一写就绿怎么办？

你为报告的 bug 写了测试，但第一次运行就通过。合理结论是？

无 JavaScript 时查看答案

答案是 B。测试必须先证明自己能对目标缺陷变红。
