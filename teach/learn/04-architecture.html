架构就是：
什么放在哪里

这个项目没有神秘的“魔法层”。它只是把静态事实、纯计算、界面状态、服务器边界和个人数据分开。维护时先找正确层，改动自然会变小。

THE MOST IMPORTANT SPLIT

番剧事实与个人状态不是同一种数据

静态番剧目录

所有用户共享。位于 data/anime.js 和历史生成目录；发布时随代码打包。

个人账号数据

按邮箱隔离。由认证 API 读写 D1，包括会话、追番与单集已看。

前者像竞赛题面和官方数据，所有选手共享；后者像每位选手的提交记录，必须由服务端按身份隔离。
存储不变量排期不是运行时从 D1 查询；用户身份也不能从静态目录或浏览器 JSON 得出。

DIRECTORY MAP

目录不是按文件后缀分，而是按责任分

区域回答的问题典型文件
data/事实是什么？data/anime.js、生成目录、封面图集映射
lib/如何纯计算或校验？lib/calendar.js、搜索、统计、认证密码工具
app/页面显示什么、请求如何进入？app/page.tsx、app/api/、app/auth.ts
db/ + drizzle/个人数据如何持久化？schema、连接、迁移历史
scripts/静态数据如何生成？AniList/YUC/Syoboi/封面脚本
worker/ + 构建配置代码如何成为线上 Worker？Worker 入口、Vite、Sites 打包插件
tests/哪些行为和约束不能退化？算法、数据、认证、渲染后 HTML 测试
rg --files app lib data db scripts tests | sed -n '1,160p'

GENERATED FILES

先判断“这是源码还是产物”

可直接维护

app/、lib/、schema、脚本和手工维护的当前季目录。

通过脚本更新

data/yuc-history-<year>.js、data/syoboi-history-<year>.js、data/cover-sprites.js 和图集。

构建产物

dist/、.next/、.wrangler/。不手改、不提交秘密或本地状态。

迁移历史

drizzle/ 由 schema 生成后提交。能审查，但不能与 schema 脱节。

生成不变量如果文件的权威来源是脚本或 schema，修复应发生在来源或生成流程，而不是只修最终产物。

IMPORTS AS GRAPH

import 块就是局部依赖图

app/page.tsx
 ├─ data/anime.js              静态目录
 ├─ data/cover-sprites.js      封面映射
 ├─ lib/calendar.js            日期与布局
 ├─ lib/anime-statistics.js    进度与今日统计
 └─ lib/anime-episode-views.js 单集已看规则

如果页面 import 了一个函数，它是消费者；函数真正的规则通常应在被 import 的文件中维护。反过来，如果 JSX 里重新写日期或集数算法，就产生了两份规则。

依赖图像有向图：边 A → B 表示 A 需要 B。修 B 可能影响所有入边消费者；修 A 的显示通常不该改变 B 的数学定义。

WHERE SHOULD IT LIVE?

新代码应该放哪一层

需求首选位置原因
计算某周应出现的集数lib/calendar.js纯计算，可独立测试，桌面与移动复用
