React：视图 = 状态的函数

1整章灵魂：UI = f(state)

你在数学里早就习惯一句话：函数，给同样的输入，必得同样的输出。y = f(x) 里，x 定了，y 就被唯一确定，没有别的可能。React 组件（Component）就是这样一个纯函数：

类比：把 React 组件想象成 f，把「状态 state」想象成自变量 x，把「界面 UI」想象成因变量 y。给组件一份状态，它就返回一份界面；同一份状态，永远返回同一份界面——和纯函数一样可预测、可推理。

由此推出 React 的第一条铁律：你永远不直接改界面，只改状态；状态一变，界面自动跟着变。这条铁律把写界面分成了两派：

命令式（旧路子）声明式（React 路子）
你怎么想“把第三个格子涂成粉色”“状态 s 对应的界面就该长这样”
你写什么一步步操作 DOM：找到节点、改属性、改文字描述「给定状态，界面是什么」，其余交给 React
类比用指针逐个改内存单元写递推式 an=an-1+1，让机器自己跑
谁负责同步你自己手动保证「界面 = 数据」React 自动保证，你永远不用操心哪里忘了刷

同一件事——「显示当前是第几周」——两种写法对比一下，差别就清楚了：

命令式 vs 声明式：显示当前周
// 命令式（旧路子）：自己找到那个节点，再自己改它上面的文字
document.querySelector("#week-label").textContent = "7/6 – 7/12";

// 声明式（React）：描述「给定 activeWeekStart，标签就该显示这个」
// <h2>{activeWeekStart} – {weekEnd}</h2>
setActiveWeekStart(nextMonday);   // 改状态，React 自动把标签重画成新一周

命令式写界面，就像 C++ 里写 for (int i = 0; i < n; i++) a[i] = … 逐个改内存：每一步都得你自己说清楚，漏一步界面就和数据对不上。声明式则像你写递推式描述「关系」，把「怎么一步步执行」交给框架。对一个有几十个状态、上百处交互的日历页，声明式是唯一能维护的写法——这也是为什么这个项目选了 React。

先记住结论：读 React 代码，永远问三个问题：① 这里的状态（state）是什么？② 这个组件函数返回了什么界面？③ 谁在什么时候改了状态？抓住这三点，2100 行的 app/page.tsx 就不再可怕。

2组件 = 返回 JSX 的函数

React 里「组件」这个名字很唬人，本质就是一个普通 JavaScript 函数，它接收参数、返回界面描述。最小例子：

示例（教学用，非项目代码） 一个组件
function Greeting({ name }) {
  return <p>你好，{name}</p>;
}

// 用它：<Greeting name="小明" />  →  界面上显示：你好，小明

拆开看，它和 C++/Python 的函数一模一样：

  • function Greeting({ name })——函数名、参数列表，完全照旧。这里的 { name } 是「解构参数」，等价于 Python 的 def f(*, name) 或 C++ 里从 struct 里取字段。
  • 参数叫 props（properties 的缩写），就是「组件的入参」，只读。你可以在里面读 name，但不能给它赋值——就像 C++ 的 const 参数。
  • return <p>…</p>;——返回的那段像 HTML 的东西叫 JSX，就是这个组件「输出」的界面。

JSX 是什么：在 JS 里直接写“类 HTML”

JSX 看着像 HTML，但它不是 HTML——它是 JavaScript 的「语法糖」。编译时（React 项目由构建工具转换），<p>你好，{name}</p> 会被翻译成一次普通的函数调用，就像 printf 那样最终变成一堆数据。所以规则很简单：

  1. JSX 标签是「界面的模板」，最终都会变成函数调用，不产生魔法；
  2. 花括号 { } 里写任意 JS 表达式——变量、算术、三元、函数调用都行，相当于 printf 里的 %s 占位符，把值「插」进模板；
  3. 表达式有结果、语句没有：所以 {name}、{a + b}、{x ? "是" : "否"} 合法，{if (x) …} 不合法（if 是语句，没有值）。
类比：JSX 里的 {name} 就是 C 的 printf("你好，%s", name) 里的占位符——模板 + 插值。区别只在于，React 的「模板」不是字符串，而是能描述整棵界面树的结构。

两个约定，先记下别深究：① 组件函数名必须大写字母开头（Greeting），小写的会被当成普通 HTML 标签；② 返回的 JSX 必须是一个根元素——和 C++ 函数只能 return 一个值是同一个道理。

props 可以一次传好几个字段，长得就像 C++ 的 struct：

示例（教学用） 多字段 props
function AnimeCard({ title, weekday, time }) {
  return (
    <div>
      <strong>{title}</strong> 每周{weekday} {time} 播出
    </div>
  );
}
// 用：<AnimeCard title="某番" weekday="三" time="23:30" />

{ title, weekday, time } 这种「从对象里挑字段」的解构，等于 C++ 里先定义 struct Props { string title, weekday, time; }、再写 void f(const Props& p)——区别只是 React 帮你把「字段名 = 形参名」自动对上了：父组件传什么字段，子组件就收什么字段，一个不多一个不少。把这一节的几个名词收个尾：

组件 component
一个返回 JSX 的函数，界面的「积木」。
JSX
在 JS 里写「类 HTML」的语法糖，编译成函数调用。
props properties
组件的入参，只读，由父组件传给子组件。
渲染 render
把组件函数执行一遍、算出界面结果的过程。

3列表渲染：map/filter，还有 key

番剧日历里最常出现的就是「一列卡片」：一周 7 天、一天几十部番、每部番一张卡片。在 React 里，你不写循环去一个个拼界面，而是用 map/filter 从数据数组直接「生成」一列元素——这就是竞赛里你天天写的 Python 列表推导式：

示例（教学用） 列表渲染 ≈ 列表推导式
// Python 里你会写：
//   cards = [AnimeCard(a) for a in anime if a.season == "2026-07"]
// JS/React 等价写法（两段式：先筛，再映射成元素）：

animeList
  .filter((a) => a.season === "2026-07")              // 留下 7 月番
  .map((a) => <AnimeCard key={a.id} anime={a} />);    // 每部生成一张卡片

这几乎是本项目里出现频率最高的句式。你在 app/page.tsx 里会反复看到它——真实代码长这样：

app/page.tsx 第 323～328 行（真实代码，节选）
const calendarAnime =
  activePage === "mine"
    ? allAnime.filter((record) => selectedAnimeIds?.includes(record.id)) // 「我的番剧」页：只留收藏的
    : allAnime;                                                          // 其余页：全库

const searchResults = allAnime.filter((record) => matchesAnimeTitle(record, animeQuery)); // 全库搜索

读代码时，.filter(...).map(...) 就是「先筛选、再逐项变元素」，和列表推导式一个读法：filter 的箭头函数是「留下的条件」（返回 true 才保留），map 的箭头函数是「每一项变成什么」。中间那个 ? : 就是 C 系的三目运算符，selectedAnimeIds?.includes(...) 里的 ?. 是「前面是 null 就短路返回 null、不报错」的可选链。

key：React 认「谁是谁」的身份证

当你一次生成几十张卡片，React 需要知道这次渲染里的第 3 张卡，和上次渲染里的哪张是同一个，才能高效地只更新变化的部分（而不是推倒重来）。它靠的就是 key 属性：

类比：key 就像数组下标 / 哈希表的键——它回答「这个元素是谁」。但它比下标更严格：必须稳定且唯一。就像数据库里的主键 id，而不是「这一秒它在列表里的位置」。
千万别拿会变的 index 当长期标识：用 map((a, i) => … key={i}) 当列表会增删、重排时，同一部番会「借」到别人的 key，导致状态错乱。本项目的约定非常明确——每部番都有一个稳定且全局唯一的 id（在 data/anime.js 里），所以永远写 key={a.id}，这是项目铁律，第 05 章会再强调。

本项目里的 key 全是「稳定字段」拼出来的，正好当范例：

app/page.tsx 第 1671、967 行（真实代码，节选）
// 网络放送列表里的番剧卡片：用番剧的稳定 id
<button className="network-card" key={record.id} …>…</button>

// 时间轴上的节目卡：一部番 + 一段集数，拼成「唯一的一集」
key={event.id + "-" + event.episodeStart + "-" + event.episode}

第二行是重点：一集的身份是「哪部番 + 从第几集到第几集」三个字段拼出来的字符串。只要这三个字段稳定，key 就稳定；哪怕这张卡在时间轴上的位置挪了，React 也认得它是同一集，不会和别的集搞混。这就是「稳定唯一」的真实含义——身份来自数据本身，而不是来自位置。

4state 与 useState：会变、且影响界面的量

现在回到那个等式。状态（state）就是「会变、并且一变界面就要跟着变的量」。React 给你一个工具来声明它，叫 useState：

示例（教学用） useState 的基本用法
import { useState } from "react";

const [count, setCount] = useState(0);
// ↑ 返回一个长度为 2 的「元组」：当前值 + 唯一能改它的更新函数

setCount(count + 1);   // ✓ 传一个新值，触发重新渲染
// count = count + 1;  // ✗ 没用：count 只是本次渲染的快照，直接改它不重画

三个点，逐个翻译成你熟的东西：

  • 「元组」解构：const [a, b] = … 就是 C++ 的 auto [a, b] = make_pair(…) / std::tie，或 Python 的 a, b = (…, …)。左边两个名字是「别名」，不是语法黑魔法。
  • setXxx 触发重渲染：调用 setCount 后，React 会把整个组件函数重新执行一遍，用新的 count 重新算出界面。这正对应「f 重算一遍得到新的 y」。
  • 不可变更新：你永远「传一个新值」而不是「原地改旧值」。数组加一项、对象改一个字段，都要先复制：
示例（教学用） 不可变更新
setTodos([...todos, newItem]);      // 数组：铺开旧数组 + 新元素，得到全新数组
setObj({ ...obj, done: true });     // 对象：铺开旧字段 + 覆盖 done，得到全新对象

这其实是你熟悉的函数式风格：不修改传入的数据，而是返回新数据。React 靠「新值和旧值不是同一个引用」来判断你确实想变，所以直接改旧对象再传回去（引用相同）会被它忽略——这是新手最容易踩的坑。

判断「这是不是 state」的三问：① 它会变吗？② 它变了，界面要跟着变吗？③ 它能不能从别的 state 推导出来？——如果①②是「是」而③是「否」，就用 useState。而永不改变的常量，直接放到组件函数外面去定义（像全局常量），别浪费一个 state。比如项目里的季度列表 seasons、全库 allAnime 就是纯数据常量，根本不用 state。

把「state」「普通变量」「常量」三样放在一起，边界就清晰了：

种类会不会变变了界面要不要重画怎么做
常量不变—放组件函数外面（如 seasons、allAnime）
中间变量随 state 变它由 state 推导而来，自己不用存组件里直接 const x = … 算出来
state会变一变界面必须重画useState
练一下：下面三个量，哪些该用 useState？① 当前选中的周 activeWeekStart；② 本周 7 天的数组 weekDays(activeWeekStart)；③ 固定的季度列表 seasons。先自己想，再点开看答案。
参考答案

只有 ① 该用 useState：它会变，而且一变界面要重画。② 是「由 ① 推导」的中间量，每次渲染现算即可，存成 state 反而会「两份数据不同步」。③ 是不变的常量，直接定义在组件外面。记住口诀：能算出来的别存，不会变的别用 state。

5事件处理与 useEffect

事件：onClick 收一个函数

用户点按钮，界面才需要变。React 里给元素绑事件，就是把一个函数交给 onClick 之类的属性——完全就是 C/C++ 里「把函数指针传给回调」：

示例（教学用） 事件绑定
<button onClick={handleClick}>点我</button>    // ✓ 传函数本身（函数指针）
<button onClick={handleClick()}>点我</button>  // ✗ 渲染的瞬间就执行了，还把返回值当成回调

整个日历的所有交互——点节目卡开详情、点周按钮换周、点追番开关收藏——都是同一句式的组合：某个事件触发某个 handler，handler 里调 setXxx 改状态，状态一变界面自动更新。你不写任何「手动刷新界面」的代码。项目里真实的 handler 也全是这个句式，比如右下角主题切换按钮：

app/page.tsx 第 454～456 行（真实代码）
const toggleTheme = () => {
  applyTheme(theme === "dark" ? "light" : "dark", true);
};

读作：点一下——现在暗色就切亮、否则切暗，并记成「用户手动选择」。绑定它的按钮在 JSX 里就是 <button onClick={toggleTheme}>：handler 是普通函数，按钮是普通按钮，没有任何魔法。

useEffect：和「外界」打交道的时机

组件函数应该是纯函数（输入→输出，无副作用）。但现实里你总要和外界打交道：发起网络请求、监听系统事件、直接操作 DOM 节点。这些「副作用」要放进 useEffect，让 React 在合适的时机替你执行，而不是在渲染过程中乱来。这是项目里的真实代码——主题跟随系统：

app/page.tsx 第 439～452 行（真实代码，注释有精简）
useEffect(() => {
  const systemTheme = window.matchMedia("(prefers-color-scheme: dark)");
  const followSystemTheme = () => {
    try {
      if (localStorage.getItem("ac-theme")) return; // 用户手动选过就不跟随系统
    } catch {
      // localStorage 不可用时按未手动选择处理。
    }
    applyTheme(systemTheme.matches ? "dark" : "light", false);
  };

  systemTheme.addEventListener("change", followSystemTheme);      // 订阅「系统换主题」事件
  return () => systemTheme.removeEventListener("change", followSystemTheme); // 清理：卸载时退订
}, []);

读这个片段的四个要点：

  1. useEffect(fn, deps) 第一个参数是要执行的副作用函数，第二个是依赖数组；
  2. 依赖数组 [] 为空 = 「只在组件挂载（第一次出现）时跑一次」——这里就是「进页面时接上系统主题」；
  3. 副作用里 addEventListener 订了一个系统事件（和竞赛里挂信号处理器一个思路）；
  4. 函数末尾 return 的那个函数是清理函数：组件卸载（离开页面）时 React 调它，把刚才的 removeEventListener 执行掉——就像 C++ 析构函数负责释放资源，避免「泄漏监听器」。
类比：构造函数里 new、析构函数里 delete，必须成对出现，否则内存泄漏。useEffect 的「订阅 + 清理」是同一件事：效果函数里订阅，返回的清理函数里退订。项目里还有好几个 useEffect（比如详情弹窗打开时 showModal()），全是同一个套路，读到就套这个模板。

再看一个「依赖数组非空」的真实例子——详情弹窗：

app/page.tsx 第 458～462 行（真实代码）
useEffect(() => {
  if (selected && dialogRef.current && !dialogRef.current.open) {
    dialogRef.current.showModal();
  }
}, [selected]);

注意最后的依赖数组是 [selected]，不是 []：意思是「每当 selected 变化就执行一次」。你点某张卡片 → setSelected(那部番) → 这个 effect 发现「有选中项、且弹窗还没开」→ 调用原生 showModal() 打开弹窗。这正是大纲说的第三种副作用场景——直接操作 DOM 引用：弹窗是原生 <dialog>，开关这种事 React 不替你管，得靠 useEffect 自己动手。

6回到真实项目：Home 组件的「状态全集」

现在打开 app/page.tsx，找到 export default function Home()（第 271 行）。函数体一开头，就是整页的状态全集——数一下：第 272～292 行，一共 21 个 useState。这几个是你打开页面第一眼会撞上的：

app/page.tsx 第 272～292 行（真实代码，节选 4 个）
const [activePage, setActivePage] = useState<Page>("all");   // 当前页：播出表 / 我的番剧 / 统计 / 查询
const [selected, setSelected] = useState<SelectedAnime | null>(null); // 详情弹窗里点开的那部番
const [watchedEpisodes, setWatchedEpisodes] = useState<WatchedEpisode[] | null>(null); // 逐集已看标记
const [activeWeekStart, setActiveWeekStart] = useState(initialWeekStart); // 周历当前是哪一周

逐行翻译，你会立刻明白「整页就是这些状态的函数」：

  • activePage：当前在哪个页（播出表 / 我的番剧 / 追番统计 / 查询结果）。切页面 = setActivePage，整个页面随之重画。
  • selected：详情弹窗打开时，里面放的那部番；null 表示「没打开弹窗」。点某张卡片 = setSelected(那部番)，弹窗出现。
  • watchedEpisodes：你标记过的「第几集已看」的列表，null 表示还没从服务器加载完。
  • activeWeekStart：周历当前是哪一周（一个周一日期）。翻周按钮 = 改这个值，然后下面 eventsForWeek(allAnime, activeWeekStart) 用它算出这一周的排期——这正是「改 x，f 重算 y」。

从第 271 行往后，函数体里剩下的几百行，全是「由这些 state 算出来的中间量」和「最终返回的 JSX」——就像你写一个巨大函数，前面声明变量、中间算值、最后 return。随便挑一条链，就能看到「改 x → f 重算 y」的完整因果：

app/page.tsx 第 322、376 行（真实代码）——状态驱动的计算链
const dates  = weekDays(activeWeekStart);                          // 由「当前周」推出 7 个日期
const events = eventsForWeek(calendarAnime, activeWeekStart);      // 由「当前周 + 数据」推出本周排期

你翻到下一周，只做一件事：setActiveWeekStart(下一周周一)。React 重跑 Home()，上面两行用新的 activeWeekStart 重新算出 7 个日期和整周排期，界面就翻过去了。你没写任何「清空旧周、重画新周」的代码——这正是 UI = f(state) 的威力。读它的正确姿势是：先扫一眼 21 个 state（这是 x 的全集），再挑一条感兴趣的状态看它在哪里被 setXxx、又如何影响界面，不要试图从头读到尾。

最后两个词，各记一句话即可（现在不展开）：

use client client component
文件顶部一行指令，意思是「这个组件在浏览器里跑、带状态和交互」。这个项目里 app/page.tsx 就是客户端组件，所以它才能用 21 个 useState。
hydration 水合
服务器先发一版「静态 HTML」让你秒看到画面，随后 React 在浏览器里「接管」这版 HTML、把事件和状态接上去的过程。你可以先理解为「先显示、再通电」。

把整章压缩成一张「读 React 代码速查卡」，以后打开任何 React 文件照着做：

  1. 找到组件函数（export default function Xxx() 或 function Xxx()）；
  2. 扫一眼函数开头的 useState——这是它的状态全集 x；
  3. 看 return 里的 JSX——这是它画出来的界面 y；
  4. 找 setXxx 出现在哪些事件 / useEffect 里——这是「谁在改状态」；
  5. 剩下的 filter/map、useEffect、onClick，套本章模板逐个翻译。
本关目标自检：这一章的目标是「能读懂 React 代码」，不是「从零手写 React」。判断标准很简单——给你 app/page.tsx 里任意一行，你能说出「这是 state / 这是由 state 算出来的值 / 这是 JSX / 这是在改状态」四选一，就达标了。看不懂的细节（比如 useSyncExternalStore、useRef）先跳过，它们只是 useState 的亲戚，原理一样。

7本章测验

1.（单选）「UI = f(state)」这个等式，最准确的理解是？

方向别搞反：状态是因，界面是果。和 y = f(x) 一样，x（状态）决定 y（界面），不是反过来。你只改状态、从不手改 DOM，这正是「声明式」与「命令式」的分界线。

2.（多选）下列哪些操作会真正触发 React 重新渲染（让组件函数重新执行）？

只有「通过 setXxx 传一个新引用」才会触发重渲染（A、C）。B 里 count 只是本次渲染的快照，直接改它 React 根本不知道；D 传的是同一个对象引用，React 用引用比较判断「没变」，于是不重画——所以必须「复制一份再改」。

3.（单选）useState(0) 这一句，返回的是什么？

useState 返回一个二元组，习惯上用数组解构 const [值, 更新函数] = useState(初值) 接住——和 C++ 的 tie / Python 的 a, b = ... 是一个意思。第一个是当前值（只读），第二个是唯一能改它的函数。

本章小结（考前默写一遍，读代码就不会慌）：

  • 界面是状态的纯函数——只改状态，从不手改 DOM；
  • 组件 = 返回 JSX 的函数，props 是只读入参，{ } 里插表达式；
  • 列表用 filter/map 生成，key 必须稳定唯一，用数据的 id 而不是下标；
  • useState 返回 [值, 更新函数]，改值要「传新引用」而不是原地改；
  • 副作用（请求、订阅、操作 DOM）放进 useEffect，盯紧依赖数组。
