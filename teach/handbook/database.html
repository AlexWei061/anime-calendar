TASK 06 · DATABASE

修改 D1 表、约束
或数据库迁移

把 schema 当作定义，把迁移当作“从旧状态到新状态的证明步骤”。二者必须一致；本地能跑不代表已有生产数据能安全升级。

成功标准

  • db/schema.ts 表达目标结构，迁移由 npm run db:generate 生成并经过人工审阅。
  • 升级已有数据库不会无意丢失追番、已看、账号或会话数据。
  • 主键、唯一键、非空、默认值和索引支持 API 的实际查询语义。
  • .openai/hosting.json 的逻辑绑定名与 getDb() 使用的 DB 一致。
  • 仓库不包含真实资源 ID、密钥、明文凭据或本地 D1 状态。
迁移不变量schema 描述现在，迁移描述历史；不能只改其中一边。

先读这些文件

  • db/schema.tsD1 表、列、主键和唯一约束的代码定义。
  • db/index.tsCloudflare DB 绑定到 Drizzle 的入口。
  • drizzle/按顺序应用的数据库历史；生成后必须审阅。
  • drizzle.config.tsschema 与迁移输出配置。
  • .openai/hosting.jsonSites 的逻辑 D1 声明，不含真实资源 ID。

最小修改顺序

  1. 先写数据不变量和旧数据兼容策略：新增、回填、约束、删除分别如何发生。
  2. 在 API/数据库测试中写失败行为，包含旧库升级或关键约束。
  3. 只编辑 db/schema.ts，再运行 npm run db:generate，不要先手写 SQL。
  4. 逐句审阅新迁移：表名、列名、默认值、复制顺序和可能的数据丢失。
  5. 在本地 D1 应用迁移，运行旧记录读取和新记录写入的 smoke test。
  6. 确认构建插件仍把 drizzle/ 与 hosting 声明复制进部署产物。

回归测试

升级

从旧 schema 与代表性旧记录出发，迁移后数据仍可读取。

约束

重复唯一键、缺失必填值和非法关系按设计失败。

API

注册、会话、追番和已看路径都在新 schema 上工作。

打包

构建后的 dist/.openai/ 包含声明与迁移。

验证

npm run db:generate
npm run lint -- --ignore-pattern .worktrees
npm test
git diff --check
git diff -- db/schema.ts drizzle/ db/index.ts .openai/hosting.json

生成命令之后先看 git diff，确认只产生预期迁移，再继续本地应用和全套测试。

停止并确认

数据库改动不可轻率继续：
  • 迁移包含删除表/列、重建表或不可逆数据转换；
  • 旧数据没有可靠默认值或回填来源；
  • 新唯一约束可能被已有记录违反；
  • 本地 schema、生产迁移历史或绑定名不一致；
  • 需要真实生产数据或资源 ID 才能判断安全性。
