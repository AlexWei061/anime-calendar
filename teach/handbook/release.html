风险：最高

TASK 07 · RELEASE

提交、推送或
发布一个版本

发布不是“构建成功”的同义词，而是一条证据链：当前 diff → 精确提交 → 远端祖先关系 → 同一提交的构建产物 → 部署成功状态。

成功标准

  • 提交只包含用户要求的文件，没有带上工作区中别人的改动。
  • lint、类型检查、Worker 构建、全部回归测试和 git diff --check 通过。
  • 推送前重新核对远端，目标提交是当前远端的快进后代；绝不强制覆盖。
  • GitHub 与 Sites 引用同一个已验证的 main 提交和构建产物。
  • Sites 默认保持私有，并以部署平台最终成功状态和 URL 为交付依据。
发布不变量“本地测试的代码”“GitHub 上的提交”“Sites 运行的版本”必须是同一个事实。

先读这些文件

  • package.jsonlint、test、build 与数据生成命令的真实定义。
  • worker/index.tsCloudflare Worker 运行入口。
  • vite.config.tsvinext、绑定模拟和 Sites 构建插件。
  • build/sites-vite-plugin.ts把 hosting 声明与迁移放入构建产物。
  • .openai/hosting.json逻辑资源和私有站点部署边界。

最小修改顺序

  1. 先读 git status --short 和目标 diff，把用户改动与本次改动分开。
  2. 只暂存明确范围，检查 git diff --cached --name-only 与暂存内容。
  3. 运行 lint、npm test 和 diff hygiene，记录实际退出状态。
  4. 创建单一清晰提交，再获取远端状态，确认可以快进。
  5. 只有用户明确要求时才推送或发布；并发更新先合并、重测，禁止 force push。
  6. 发布后等待平台最终状态，核对提交、迁移、资源绑定、访问范围和 URL。

回归测试

代码

lint、类型、构建和全部 Node 测试以退出码 0 完成。

提交

暂存文件清单与用户范围逐项对应，不含凭据和生成缓存。

远端

目标提交是远端最新提交的后代，推送不需要强制。

部署

Worker、D1 迁移、图集和私有访问在最终版本中可用。

验证

git status --short
git diff --check
npm run lint -- --ignore-pattern .worktrees
npm test
git diff --cached --name-only
git log -1 --oneline

任何一步失败，修正后从受影响的验证重新开始；不能把旧成功构建当作后来提交的证据。

停止并确认

这些动作需要明确授权或新证据：
  • 用户只说“完成”，没有要求推送、部署或改变可见范围；
  • 远端出现本地没有的提交；
  • 测试、lint、构建或部署状态不是成功；
  • 暂存区含用户未要求的文件、凭据或大批生成物；
  • 需要 force push、回滚数据库或公开私有站点。
