TASK 05 · AUTH

修注册、登录、
会话或头像身份

认证问题最容易被一句“登录失败”混在一起。正确顺序是：浏览器是否收到 Cookie → 后续请求是否带上 → 服务器是否验出会话 → 数据库里是否存在且未过期。

成功标准

  • 密码只以 PBKDF2 哈希保存，会话只保存令牌的 SHA-256 哈希。
  • Cookie 保持 HttpOnly、SameSite=Lax、Path=/。
  • 仅 HTTPS 请求添加 Secure；本地/LAN HTTP 可建立会话，生产 HTTPS 仍受保护。
  • 注册、登录、退出、/api/auth/me 和受保护 API 使用同一会话判断。
  • 错误路径不泄露密码、令牌或用户枚举细节。
认证不变量用户身份由服务器验证后的会话决定，而不是组件状态、请求正文或 URL 参数。

先读这些文件

  • app/auth.ts签发、读取、销毁会话和 Cookie 属性。
  • lib/auth.js输入校验、PBKDF2、令牌生成与 SHA-256 哈希。
  • app/api/auth/login/route.ts登录凭据验证和签发 Cookie。
  • app/api/auth/me/route.ts浏览器恢复当前登录用户的事实来源。
  • tests/auth-client-flow.test.mjs登录、Cookie 与当前用户恢复的客户端链路回归。

最小修改顺序

  1. 记录完整请求链：登录响应 Set-Cookie、浏览器存储、/api/auth/me 请求 Cookie、响应。
  2. 分别在 HTTP 与 HTTPS 条件下写失败测试，避免把环境差异误判为密码问题。
  3. 检查输入/哈希纯函数，再检查 route，最后检查会话/D1；不要先改 UI。
  4. 保持普通路径和错误路径使用等价密码计算，避免明显时序泄漏。
  5. 做最小修复，不通过移除 HttpOnly 或放宽 SameSite 来“让它工作”。
  6. 重跑所有受保护 API 测试，因为它们共享同一身份边界。

回归测试

Cookie

HTTP 无 Secure，HTTPS 有；两者保留 HttpOnly、SameSite 与 Path。

密码

正确密码通过、错误密码失败；库中没有明文密码。

会话

明文令牌仅在 Cookie；数据库保存哈希，过期/退出后不能复用。

授权

追番和已看 API 对无会话请求稳定返回 401。

验证

node --test tests/auth.test.mjs tests/auth-client-flow.test.mjs
npm run lint -- --ignore-pattern .worktrees
npm test
git diff --check

本地验证至少覆盖 HTTP 与生产形态 HTTPS；两者 Cookie 属性本来就不完全相同。

停止并确认

安全边界不能靠猜：
  • 需求要求降低 HttpOnly、SameSite、密码强度或会话熵；
  • 需要查看、记录或迁移真实用户凭据和令牌；
  • 数据库 schema 与现有迁移对不上；
  • 故障只在特定代理/域名出现，需要外部基础设施证据；
  • 修复准备把邮箱从浏览器正文当作身份。
