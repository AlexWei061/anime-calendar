1心智模型：Node、npm 是什么

你之前学 JS，它大多活在浏览器里；但浏览器没有文件系统、没有进程、不能开服务器。Node.js 让 JS 离开浏览器、直接在电脑上跑——就像 Python 的解释器 python。有了它，JS 也能读文件、跑脚本、开服务。

Web/Node 世界Python 世界的对应物干什么
Node.jspython 解释器执行 .js/.mjs 文件
npmpip包管理器，装第三方库
package.jsonrequirements.txt + 构建脚本声明依赖和版本，还声明一堆 scripts 命令
node_modules/site-packages/装好的库，体积巨大，不提交进 git
npxpython -m临时运行一个包的命令，不必全局安装
类比：pip install numpy 把 numpy 装进 site-packages，然后 import numpy 就能用；对应地 npm install 把依赖装进 node_modules，然后 import 就能用。python script.py 对应 node script.mjs。唯一区别：Node 用 package.json 显式记录每个依赖及其版本，而不是靠"我记得我装过"这种脑内记忆。

两个容易混的细节：

  • package.json 记录"我要什么"（依赖名 + 兼容范围）；package-lock.json 记录"我实际装了哪一版"（完整依赖树的精确锁定）。两者都提交进 git，保证队友 npm install 装出来和你一模一样。
  • 项目顶部有 "type": "module"，声明这是 ES Module 项目——所以源码用 import/export，测试文件后缀是 .mjs（module JS）。这就像"这是 .py 而不是 .pyc"，是模块系统的标记。

这个项目对 Node 版本有硬性门槛：

package.json engines 字段
"engines": {
  "node": ">=22.13.0"
}

太旧的 Node 会缺 API（比如 node:test 的某些特性）。装环境第一步，先 node --version 确认版本达标。

几个要点：

  • WRANGLER_LOG_PATH=.wrangler/wrangler.log 是环境变量前缀（Linux 里 VAR=value cmd 的写法），把 Wrangler 的日志写到文件里，避免污染终端输出。
  • npm test 里的 && 是"短路与"：前一步失败，后面就不跑了。所以它是类型检查 → 构建 → 测试的三步流水线。
  • npm run lint 仓库约定还要额外加 --ignore-pattern .worktrees（嵌套 worktree 场景），见 AGENTS.md 的"开发与验证"一节。
数据 / 封面脚本有顺序：改排期数据时，顺序是 AniList → YUC 目录 → しょぼい快照 → 再生成 YUC 目录；改封面时先 convert:covers-webp 再 generate:cover-sprites。顺序反了，合并或打包结果会缺字段。这些生成出来的文件都标注"不得手工编辑"——改完记得跑对应脚本，再跑测试。

第一次克隆项目，先 npm install 把依赖装进 node_modules/，之后 npm run xxx 才找得到工具。日常你基本不需要碰 node_modules/——它只是"工具的家"，改了没意义，删了重装即可。

3dev 与 build：开发态 vs 生产态

同一个项目活在两个"世界"里：

dev

开发服务器（npm run dev）

源码即真相，改一行立刻热更新，反馈要快。像竞赛里"本地跑样例"，随时改随时看，不在乎启动慢一点。

build

生产构建（npm run build）

把源码打包压缩成体积小、启动快的产物放进 dist/，Cloudflare Worker 运行时用它。像交卷前把程序编译成最终可执行文件。

构建产物的关键区别：改了源码不重新 build，部署出去的东西不会变。下面这些目录都是"生成物"，不要手改、不要提交（它们已被 git 忽略）：

目录谁生成的为什么别碰
dist/npm run build打包产物，下次 build 整个覆盖
.next/Next 开发 / 构建中间缓存缓存，可随时删
.wrangler/Wrangler 本地状态与日志本地状态，可能含敏感信息，不可提交
顺带一提：build/sites-vite-plugin.ts 在构建时会把 .openai/hosting.json 和 drizzle/ 复制进 dist/.openai/。所以你直接往 dist/ 里塞东西没用——它每次构建都被重建。要改部署相关的东西，去改真正的源文件。

5静态检查：改完先让编译器帮你找 bug

tsc --noEmit：只检查，不产出

TypeScript 编译器 tsc 会把 .ts 编译成 JS；加 --noEmit 后它"只查不产"——像竞赛里"只编译不运行"，让类型系统在程序跑起来之前就把错误报出来。其中最关键的是 strict null 检查：类型是 string | null 的值，必须先判 null 才能用，否则报错。

这正好解释了上一章 getSessionUser(): Promise<SessionUser | null> 为什么逼着每个调用点写 if (!user) return ...——类型系统在强制你处理"未登录"这个分支，漏了就直接编译报错，而不是等到线上才发现空指针。

报错怎么读：格式是"文件:行:列 + 错误码 + 信息"，例如 app/auth.ts:36:5 - error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'。常见错误码：TS2345 类型不匹配、TS2322 赋值类型不对、TS2339 属性不存在。像 OJ 的 CE/Warning，错误码可以直接搜索查含义。

strict null 检查长什么样

看一个最小例子——类型是 string | null，不判空直接当字符串用，tsc 直接报错：

概念演示 不是项目代码，只为说明报错
function upper(name: string | null) {
  return name.toUpperCase(); // ❌ 报错：name 可能是 null
}

function upperSafe(name: string | null) {
  if (name === null) return ""; // 先判空
  return name.toUpperCase();    // ✅ 这里 name 一定是 string
}
错误码含义像竞赛里的什么
TS2345传给函数的参数类型不对把 int 传进要 string 的函数
TS2322赋值类型不对给 int 变量赋了个 string
TS2339对象上不存在这个属性访问结构体里没有的成员
TS2531对象可能是 null，直接用了解引用空指针

ESLint：抓"长得像 bug"的写法

ESLint 不关心类型，关心风格和常见坑：未使用的变量、== 写成 ===、定义后没用、JSX 的无障碍（a11y）问题等。命令：

终端 静态检查两条命令
npm run typecheck
npm run lint -- --ignore-pattern .worktrees
三层防线分工：lint（风格 / 潜在 bug）→ typecheck（类型）→ test（行为）。前两层都是"静态"的，不运行代码，快；第三层才真正验证程序行为。三者不互相替代。

6测试：把"对拍"变成能自动重跑的断言

竞赛里你做对拍（暴力 vs 正解）、手造数据、拿样例验证。单元测试就是把这件事固化下来：给输入 → 断言输出，之后每次改动都自动重跑，谁改坏了立刻报警。

node:test + assert：Node 内置，不用装框架

node:test 提供 test() 函数；node:assert/strict 提供 assert.equal / deepEqual / match / throws 等断言。它们都是 Node 内置模块、零依赖——这也是为什么本项目 package.json 里没有任何测试框架。

tests/calendar.test.mjs 一个真实测试（节选，省略其余导入与测试）
import assert from "node:assert/strict";
import test from "node:test";
import * as calendar from "../lib/calendar.js";

const { seasonForWeek } = calendar; // 真实文件解构了 20+ 个导出，这里只留用到的

const seasons = [
  { id: "2024-april", firstWeekStart: "2024-04-01" },
  { id: "2025-january", firstWeekStart: "2024-12-30" },
  { id: "2025-april", firstWeekStart: "2025-03-31" },
  { id: "2025-october", firstWeekStart: "2025-09-29" },
  { id: "2026-january", firstWeekStart: "2025-12-29" },
  { id: "2026-april", firstWeekStart: "2026-03-30" },
];

test("keeps a cross-quarter week in its previous season until the next full week", () => {
  assert.equal(seasonForWeek(seasons, "2024-04-01").id, "2024-april");
  assert.equal(seasonForWeek(seasons, "2025-03-31").id, "2025-january");
  assert.equal(seasonForWeek(seasons, "2025-04-07").id, "2025-april");
  assert.equal(seasonForWeek(seasons, "2025-12-29").id, "2025-october");
  assert.equal(seasonForWeek(seasons, "2026-01-05").id, "2026-january");
  assert.equal(seasonForWeek(seasons, "2026-04-06").id, "2026-april");
});

这一串 assert.equal 翻译成人话就是："某周的 3/31 还属于上一季度 1 月番，直到 4/7 进入完整的新一周才算 4 月番"。每一个 assert 都是一句"给定输入，期望输出"——和你对拍里"这组数据暴力程序输出 X"一模一样。测试挂了，等于对拍发现暴力与正解不一致，说明有人改坏了 seasonForWeek 的跨季度归属逻辑。

assert 的几个常用招式

把竞赛里的验证动作翻译成断言，就这几条：

断言验证什么竞赛对应
assert.equal(a, b)两个值严格相等程序输出 == 样例输出
assert.deepEqual(a, b)对象 / 数组逐字段相等比较两个结构体每个成员
assert.match(s, /re/)字符串匹配正则输出里必须含某段
assert.throws(fn, Error)调用应当抛错非法输入应返回错误码

比如 assert.throws 就对应"非法输入要报错"：tests/calendar.test.mjs 里 assert.throws(() => timelineOffsetMinutes("14:59"), RangeError)，就是断言"14:59 这个越界时间必须抛 RangeError，而不是静默算出个错值"。

7修 bug 的正确姿势：红 → 绿 → 永不复发

这是 AGENTS.md 里反复强调的核心工作流——回归测试方法论：

  1. 红：先写一个"复现当前 bug 行为"的测试，运行它，确认它失败。比如发现某跨季度周显示错了季度，先写 assert.equal(seasonForWeek(seasons, "2025-03-31").id, "2025-january")，现在代码是错的 → 测试红。
  2. 绿：做最小修复，让这个新测试通过，同时不破坏别的测试。
  3. 守护：提交。以后任何人改坏这个逻辑，npm test 立刻报警。
为什么先写测试？因为 bug 的本质是"代码的实际行为 ≠ 我们以为的行为"。先把"以为的正确行为"用断言写死，修复才有靶子，也能证明你真的修对了——而不是"看起来好了"。这和竞赛里"先确定正解输出，再修 WA 的程序"是同一个道理。

日常工作流

  1. 改代码——只动与任务直接相关的文件，别顺手格式化大文件。
  2. 跑 npm run typecheck 和 npm run lint -- --ignore-pattern .worktrees（静态两道防线，快）。
  3. 跑 npm test（类型 → 构建 → 测试三步流水线，全绿才健康）。
  4. git 提交。
改数据 / 封面之后：先跑对应生成脚本（generate:yuc-history-pilot、convert:covers-webp、generate:cover-sprites 等），再跑测试——因为测试会断言生成后的数据 / 图集，顺序反了测试会红。而且 npm test 会先做严格类型检查、再导入构建后的 Worker 检查服务端 HTML，不能只拿 tsc 糊弄过去。
动手练：打开 tests/calendar.test.mjs，找到任意一个 test(...)，逐句读出"输入是什么、期望输出是什么"。然后运行 node --test tests/calendar.test.mjs，看看绿勾长什么样。这是你第一次"亲手跑对拍"。

几个顺手的小技巧：只跑一个测试文件用 node --test tests/calendar.test.mjs；只跑一个用例按名字过滤用 node --test --test-name-pattern "cross-quarter" tests/calendar.test.mjs。排查单个失败时不用每次跑全套，先精准复现、修好，再跑一次全绿收尾。

命令速查（背下来）

  • npm run dev —— 本地开发，改代码热更新。
  • npm run typecheck / npm run lint —— 改完先跑的两道静态防线。
  • npm test —— 交付前三连：类型 → 构建 → 测试。
  • npm run db:generate —— 只在你改了 db/schema.ts 后跑。
  • npm run generate:* / convert:* —— 只在你改了数据 / 封面后跑。

8本章自测

1. npm test 一步实际做了哪三步？

package.json 写得清清楚楚：test = npm run typecheck && npm run build && node --test tests/*.test.mjs。三步全过才算健康，&& 保证前一步失败后面就不跑。

2.（多选）下面哪些是"生成物目录"，不能手改、不能提交？

dist/ 是构建产物（每次 build 覆盖）、.next/ 是中间缓存、.wrangler/ 是本地状态，三者都被 git 忽略、不可提交。而 lib/calendar.js 是真正的源码，正是你该改的地方。

3. tsc --noEmit 的作用是？

--noEmit 直译就是"不产出"：tsc 照常做全部类型检查、该报的错照报，但不会生成任何 .js 文件。它像"只编译不运行"，是改完代码后最快的一道防线。
