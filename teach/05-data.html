数据层：番剧数据从哪来

番剧日历的"排期"（哪部番周几几点播）是静态数据：用脚本从 AniList、YUC、しょぼいカレンダー抓下来，打包进网站。这一章把 data/ 目录拆开看，让你知道每份文件的来历、哪些能动、哪些碰了也会被覆盖，以及一条番剧记录从"网页上的新番表"变成"你屏幕上的节目卡"经历了什么。

数据层 前置：第 04 章项目全景图 重点：手改 vs 生成文件的边界 数据来源：AniList / YUC / しょぼいカレンダー

1数据文件地图：谁生成、能不能手改

先给你一张"户口本"。番剧数据散落在 data/ 和 public/covers/ 里，但它们的出身完全不同：有的是你亲手维护的"源代码"，有的是脚本跑出来的"编译产物"。搞错这一点，你会改了一下午，下次一跑脚本，改动全没了。

文件 / 目录谁生成的能不能手改
data/anime.js 你手动维护的入口：season 季度对象 + 2026-07 的 yucAnime 数组 + 汇总逻辑（seasons、allAnime） ✅ 能（但要守规则，见第 2、4 节）
data/anilist-<year>.js scripts/generate-anilist-pilot.mjs 从 AniList 抓的原料 ⛔ 勿手编（重跑脚本即覆盖）
data/yuc-history-<year>.js scripts/generate-yuc-history-pilot.mjs 生成的最终目录 ⛔ 勿手编
data/syoboi-history-<year>.js scripts/generate-syoboi-history.mjs 抓的电视排期快照 ⛔ 勿手编
data/cover-sprites.js scripts/generate-cover-sprites.mjs 生成的封面图集映射 ⛔ 勿手编
public/covers/yuc/sprites/ 同一个脚本生成的运行时图集图片 ⛔ 勿手编

记忆要点：整张表里只有一个文件归你管——data/anime.js。其余全是"生成文件"，地位等同于 C++ 里 make 出来的 .o 目标文件。

类比（编译产物）：你写 a.cpp，g++ 生成 a.out。你会去手改 a.out 吗？改了也白改，下次编译又覆盖回去。这里的 data/yuc-history-*.js、data/cover-sprites.js 就是"a.out"——它们的"源码"是脚本 + 数据源网站。要改内容，改脚本或改数据源，然后重跑生成，而不是手编生成结果。

2解剖一条真实记录：sayonara-lara

打开 data/anime.js，2026-07 的每一部番都是一个 JS 对象。下面是《再见 拉拉》这条记录，逐字段拆给你看：

data/anime.js（2026-07 目录，原样摘录）
{
  "id": "sayonara-lara",
  "episodeCount": 12,
  "titleZh": "再见 拉拉",
  "titleJa": "さよならララ",
  "coverUrl": "/covers/yuc/sayonara-lara.webp",
  "coverAlt": "再见 拉拉 主视觉",
  "premiereDateBeijing": "2026-07-05",

字段含义要点
id稳定且全局唯一的标识（slug）绝不能拿标题当 id——标题会改、会重复、含空格和符号。id 是数据库、追番列表、已看标记共用的"身份证号"
episodeCount总集数这里为 12
titleZh / titleJa中文名 / 日文名搜索框同时匹配两者
coverUrl逻辑封面键，不是文件路径长得像路径，但运行时并不直接读这个文件，而是用 coverSpriteFor() 查表定位图集坐标（见第 6 节）
coverAlt无障碍替代文本给读屏软件和图片加载失败时的兜底
premiereDateBeijing北京时间首播日期2026-07-05，统一 ISO 格式 YYYY-MM-DD
scheduleWeekday周几播出取 Sun～Sat，这里是周日
beijingTime北京时间播出时刻23:30；可出现 24:00、25:00（见第 3 节）
station播出平台标注这里写 YUC 周表 表示时刻来自 YUC 周表
sourceUrl数据来源 URL审计用，保留溯源价值

注意：上面这段是 data/anime.js 里字面写着的记录。当模块被 import 时，文件后半段的 withYucSources() 会给它补上审计字段——anilistId、episodeCountSource、titleSource、coverSource、premiereDateSource 等（export const anime 才带这些，yucAnime 不带）。运行时真正被 allAnime 用的是补全后的版本。

不是每条记录都长上面那样。两种常见变体：

{
  "id": "cyborg-009-nemesis",
  "episodeCount": 3,

  "titleJa": "サイボーグ009 ネメシス",

premiereKind: "network" + scheduleWeekday: null + beijingTime: null 表示这是网络配信、开播时刻还没定。它不会出现在周历的时间轴上，而是被放进首播日期专属的"网络配信 · 时刻未定"区域。铁律：没定时刻就写 null，不许编一个时刻出来。

data/anime.js · yume-mita（先行 3 话）
{
  "id": "yume-mita",
  "episodeCount": 12,
  "premiereEpisodeCount": 3,
  "titleZh": "BanG Dream! YUME∞MITA",
  "premiereDateBeijing": "2026-07-02",
  "scheduleWeekday": "Thu",
  "beijingTime": "22:00",
  "station": "YUC 周表",
  "sourceUrl": "https://yuc.wiki/202607/"

多了个 premiereEpisodeCount: 3：表示首播日一次先行放出 3 话，第 1～3 集在首播日一起播，第 4 集起才进入每周一集的固定节奏。周历展开就是靠这个字段 + 首播日期推出来的（具体算法在第 06 章）。

3凌晨时刻的约定：24:00、25:00 都是合法的

如果你看到 beijingTime: "25:00"，别以为数据错了——这是日本深夜动画的行业习惯：把"跨过午夜"的节目仍然记在"播出当天"的名下。比如周六 23:00 开播的节目被电视台排成"周六 25:00"（即周日凌晨 1 点），是为了让观众把它归到"周六晚上"这一档。

本项目完整保留这个习惯，规则是：

  • 24:00 = 次日 0 点，25:00 = 次日 1 点。数据里照写 24/25。
  • 显示时，formatBroadcastTime() 把 ≥24:00 的时刻换算成"次日 HH:MM"。
  • 凌晨 00:00～04:59 的节目，layoutBroadcast() 会把它们归到前一天的栏目里（因为观众感知上它属于"昨晚熬夜看的番"）。
lib/calendar.js · formatBroadcastTime / layoutBroadcast（第 06 章精讲，这里只看结果）
export function formatBroadcastTime(time) {
  const minutes = timeToMinutes(time);
  if (minutes < 24 * 60) return time;

  const nextDayMinutes = minutes - 24 * 60;
  return `次日 ${String(Math.floor(nextDayMinutes / 60)).padStart(2, "0")}:${String(
    nextDayMinutes % 60,
  ).padStart(2, "0")}`;
}

function layoutBroadcast(broadcastDate, broadcastTime) {
  const minutes = timeToMinutes(broadcastTime);

  if (minutes < 5 * 60) {
    return {
      date: addDays(broadcastDate, -1),
      time: formatTime(minutes + 24 * 60),
      broadcastDate,
      broadcastTime,
    };
  }

  return { date: broadcastDate, time: broadcastTime, broadcastDate, broadcastTime };
}

两条边界对照记忆：

原始 beijingTime实际时刻周历里的处理
23:30当天 23:30原样留在当天
24:00次日 00:00显示"次日 00:00"，仍在当天栏目
25:00次日 01:00显示"次日 01:00"，仍在当天栏目
01:30当天 01:30（凌晨）归到前一天，显示"次日 01:30"
踩坑提醒：不要在页面组件里手动把日期挪来挪去。这些换算必须交给 formatBroadcastTime 和现有布局逻辑做——你自己重写一遍，一定会和测试断言不一致。

4季度对象与 seasons 数组

一部番之上，还有两个层级的容器：季度对象（描述"2026 年 7 月番"这件事本身）和 seasons 数组（把 27 个季度按时间排成一条长链，支撑跨季度前后翻周）。

data/anime.js · season 季度对象
export const season = {
  "label": "2026 年 7 月番",
  "timeZoneLabel": "北京时间（UTC+8）",
  "updatedAt": "2026-07-16",
  "catalogCount": 66,
  "sourceName": "YUC 2026年7月新番表",
  "sourceUrl": "https://yuc.wiki/202607/"
};
  • label：界面季度选择器上显示的文本。
  • timeZoneLabel：提醒所有时刻都是北京时间（UTC+8）。
  • updatedAt：目录最后更新时间，审计价值，别顺手删。
  • catalogCount：这个季度目录里应该有多少部番。
  • sourceName / sourceUrl：数据出处，溯源用。

seasons 数组把 season 和 anime 装进每一项，并额外加了两个字段：

data/anime.js · seasons 数组的最后一项（2026-07）
{
  id: "2026-july",
  firstWeekStart: "2026-06-29",
  timelineStartHour: 15,
  ...season,
  anime,
}
  • firstWeekStart：该季度显示的第一周的周一。季度选择器点一下，就跳到这个周一所在的周。
  • timelineStartHour：时间轴的默认起点小时。历史季度都是 5（05:00），2026-07 是 15（15:00，因为 7 月番节目集中在晚间）。
  • 最后一项 ...season, anime：展开 season 对象，再挂上 anime 数组（第 2 节那条记录所在的数组）。
铁律：catalogCount 必须等于该季度 anime.length。tests/anime-data.test.mjs 里有断言 assert.equal(season.catalogCount, 66) 和 assert.equal(anime.length, 66)。你新增/删除一部番却没同步 catalogCount，测试会直接挂。

5数据生成管线：一条数据的三段旅程

历史季度的目录是怎么来的？四个脚本按固定顺序接力，顺序不能乱：

  1. AniList 拉原料：generate-anilist-pilot.mjs 抓某年 AniList 的首播日期、时刻、集数，写入 data/anilist-<year>.js。
  2. YUC 合并生成目录：generate-yuc-history-pilot.mjs 以 YUC 的中文名 + 封面为主，合并 AniList 排期和已有的しょぼい快照，生成 data/yuc-history-<year>.js。
  3. しょぼい抓电视排期：generate-syoboi-history.mjs 按当前目录匹配しょぼいカレンダー，抓电视台排期，生成 data/syoboi-history-<year>.js 快照。
  4. 再生成 YUC 目录：再跑一次 generate-yuc-history-pilot.mjs，把新快照合并回最终目录。这是关键：不重跑，新抓的电视排期就进不了最终目录。

合并时每条字段按来源逐项拼，优先级固定：

合并优先级：YUC → AniList → しょぼいカレンダー → 估算或 null。低优先级来源只能补空值，不能覆盖已有值；中文名与封面永远来自 YUC。已填入的字段会保留 *Source 审计标记（如 premiereDateSource: "AniList"），让你一眼看出每个值是谁给的。

为什么"只能补空、不能覆盖"？用 C++ 的话说，就是各来源的优先级是偏序，低优先级的写要变成 no-op。YUC 是"中文世界最权威的新番表"，AniList 只有日文/英文排期，しょぼい是最细的电视台时刻但可能有错——所以中文名、封面听 YUC 的，YUC 没写的时刻才轮到 AniList，AniList 也缺才轮到しょぼい，全都没有就估 12 集或写 null。

类比（按位或的合并）：类似 a |= b 只补上 a 里为 0 的位。这里每个字段是一"位"，高优先级先填，低优先级只填"还是空"的位置，绝不覆盖已经填好的值。

6封面管线：为什么封面是一张张图集

每个 coverUrl（逻辑键）背后，真正的像素不是一张独立图片，而是从图集（sprite sheet）里抠出来的。生成流程：

  1. 下载独立封面：生成目录时把 YUC 的封面图下载到本地。
  2. 转 WebP：npm run convert:covers-webp 把独立封面无损转成 WebP。
  3. 打包图集：npm run generate:cover-sprites 把全部 WebP 封面拼成 4×10、quality 90 的网格大图，生成映射文件 data/cover-sprites.js，并删除已打包的独立文件。

运行时查表函数（真实代码）：

data/cover-sprites.js（脚本生成，文件末尾）
export function coverSpriteFor(coverUrl, variant = "thumbnail") {
  const sprite = coverSprites[coverUrl] ?? null;
  if (!sprite || variant === "detail") return sprite;
  return { ...sprite, url: sprite.url.replace(/\.webp$/, "-thumb.webp") };
}

映射文件里的每一条长这样（示意其中一项）：

data/cover-sprites.js · 逻辑键 → 图集坐标
"/covers/yuc/100-girlfriends-3.webp": {
  "url": "/covers/yuc/sprites/cover-sheet-01.webp",
  "x": 0,
  "y": 0,
  "columns": 4,
  "rows": 10
}

页面要显示某张封面时，用逻辑键查表得到 url（哪张图集）+ x/y（第几格），再裁出来显示。variant 参数区分缩略图（-thumb，单元格减半）和详情大图（原格）。

为什么费这么大劲？因为发布到 Sites 的静态包有文件数量上限，上千个独立封面小文件会超标。打包成几十张 4×10 的大图，文件数立刻降下来。测试里甚至断言 public/covers/yuc/ 下的封面资源少于 100 个。
改封面后的固定动作：必须依次跑 npm run convert:covers-webp 和 npm run generate:cover-sprites 两个脚本，把新封面并入图集并刷新映射。不要手编图集或映射文件，也不要试图"恢复每部番一张独立图"——那样又会撞上文件数上限。

7本章测验

1.（多选）下面哪些是脚本生成的"编译产物"，不能手改？

A、B、D 都是脚本生成文件（yuc 目录、しょぼい快照、图集映射），改了也会被下次生成覆盖。data/anime.js 是唯一手维护的入口，能改但要守规则。同理 data/anilist-<year>.js 和 public/covers/yuc/sprites/ 也是生成产物。

2. 历史目录里，同一个字段多个来源都有值时，谁的优先级最高？

优先级是 YUC → AniList → しょぼいカレンダー → 估算/null。低优先级只能补空值、不能覆盖已有值；中文名和封面永远来自 YUC。

3. 某部番的 beijingTime 写成 "25:00"，页面上会怎么处理？

25:00 = 次日凌晨 1 点，formatBroadcastTime 会把它显示成"次日 01:00"。因为它 ≥ 05:00，layoutBroadcast 不会把它归到前一天——只有 00:00～04:59 的节目才归到前一天（观众感知上属于"昨晚熬夜的番"）。
