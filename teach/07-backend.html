后端与数据库

上一章讲的是"死数据"（番剧排期，打包进代码）；这一章讲"活数据"——你的追番列表和逐集已看标记，它们按账号隔离、永久存在云端数据库 D1 里。核心只有三个词：请求 → 校验 → 存库。跟着一次"保存追番"从头走到尾，你就把 App Router 路由、Cookie 会话、SQL 表、Drizzle ORM 全串起来了。

后端 · 数据库 前置：第 02 章 HTTP、第 05 章数据层 技术栈：Next.js App Router / Cloudflare Worker / D1 / Drizzle 核心：认证 → 白名单校验 → 原子写入

1跟着一次"保存追番"走完全程

你在日历里勾了一堆番，点"保存"。这条"活数据"的完整旅程如下：

再用步骤列表把每一步钉死（下面每一行都能在第 5、6 节找到对应源码）：

  1. 你点"保存"，浏览器把当前追番 ID 列表 fetch 一个 PUT 请求发到 /api/anime-selections。
  2. Cloudflare Worker 收到请求，按 App Router 约定把它交给 app/api/anime-selections/route.ts 导出的 PUT 函数。
  3. getSessionUser() 读 ac_session Cookie，哈希后查会话表；没登录 → 返回 401。
  4. 解析请求体 JSON（request.json()），解析失败 → 400。
  5. filterKnownAnimeIds() 做白名单过滤（丢掉不在 allAnime 里的 ID）+ 去重。
  6. 把"删除旧列表 + 分批插入新列表"放进同一个 db.batch()，D1 原子提交。
  7. 返回 Response.json({ animeIds })，浏览器据此更新界面。
类比（评测机的三段式）：做 OJ 题时，你的程序"读入 → 计算 → 输出"；这里每个 API 也是"读请求 → 校验 → 查/写库 → 输出 JSON"。差异在于：OJ 一次评测只服务你一个人，而 Worker 同时服务成千上万人，所以每一步都要假设输入可能是恶意的——这解释了为什么校验环节那么啰嗦。

2API 路由约定：文件系统就是路由表

Next.js App Router 的规矩一句话：文件路径 = URL，导出的函数 = HTTP 方法。不需要像传统后端那样手写一张"URL → 处理函数"的路由表，目录结构本身就是路由表。

文件URL导出的函数
app/api/anime-selections/route.ts/api/anime-selectionsGET（读追番列表）、PUT（整表保存）
app/api/anime-episode-views/route.ts/api/anime-episode-viewsGET（读已看）、PUT（标记/取消已看）
app/api/auth/register/route.ts/api/auth/registerPOST（注册）
app/api/auth/login/route.ts/api/auth/loginPOST（登录）

约定细节：

  • 文件必须叫 route.ts（不是 page.tsx——那个是渲染网页的，route.ts 是纯 API）。
  • 导出的函数名必须大写，对应 HTTP 方法：export async function GET()、export async function PUT(request: Request) 等。
  • 函数返回一个 Response（本项目统一用 Response.json(...)）。
类比（文件系统）：这和 #include 按路径找头文件一样——app/api/foo/route.ts 就是"URL /api/foo 的处理器"，路由表自动从目录树长出来，不用你维护任何注册代码。

3D1 与 SQL 速成 + 四张表

D1 是 Cloudflare 的托管 SQLite：一个能跑 SQL 的关系型数据库。SQL 那些术语，用你熟悉的类比一分钟说清：

表 table
一张二维表格，类似 C++ 里 vector<struct> 的"struct 定义"——规定每行有哪些列。
行 row
一条记录，相当于 struct 的一个实例。
列 column
记录的一个字段，相当于 struct 里的成员变量。
主键 primary key
唯一标识一行的字段（组）。像 unordered_map 的 key，同一张表里不允许两行主键相同。
复合主键 composite key
用多个列合起来当唯一标识。相当于 pair<A,B> 作为 map 的 key。

本项目四张表，全写在 db/schema.ts：

db/schema.ts（全文）
import { integer, primaryKey, sqliteTable, text } from "drizzle-orm/sqlite-core";
export const users = sqliteTable("users", {
  email: text("email").primaryKey(),
  passwordHash: text("password_hash").notNull(),
  displayName: text("display_name").notNull(),
  avatarVersion: text("avatar_version"),
  createdAt: integer("created_at").notNull(),
});
export const authSessions = sqliteTable("auth_sessions", {
  tokenHash: text("token_hash").primaryKey(),
  userEmail: text("user_email").notNull(),
  expiresAt: integer("expires_at").notNull(),
});
export const animeSelections = sqliteTable(
  "anime_selections",
  {
    userEmail: text("user_email").notNull(),
    animeId: text("anime_id").notNull(),
  },
  (table) => [primaryKey({ columns: [table.userEmail, table.animeId] })],
);

export const animeEpisodeViews = sqliteTable(
  "anime_episode_views",
  {
    userEmail: text("user_email").notNull(),
    animeId: text("anime_id").notNull(),
    episodeStart: integer("episode_start").notNull(),
    episode: integer("episode").notNull(),
  },
  (table) => [
    primaryKey({
      columns: [table.userEmail, table.animeId, table.episodeStart, table.episode],
    }),
  ],
);
表主键存什么
usersemail（单列）账号：邮箱、密码哈希、昵称、头像版本、注册时间
auth_sessionstoken_hash（单列）登录会话：会话令牌的哈希、所属邮箱、过期时间
anime_selectionsuser_email + anime_id（复合）追番：某个用户追了哪部番，一行一条
anime_episode_viewsuser_email + anime_id + episode_start + episode（四列复合）已看：某个用户看了某部番的某单集，一行一条

两个注意点：

  • anime_selections 的复合主键保证"同一个用户 + 同一部番"最多出现一行——主键重复的 insert 会被拒。
  • anime_episode_views 的主键里 episode_start 和 episode 通常相等（单集），但旧版遗留过"连播范围"记录（start < episode），所以两列都得进主键。第 6 节会看到它怎么被迁移。

4Drizzle ORM：用 TypeScript 描述表，再生成 SQL 迁移

你看到的 db/schema.ts 不是 SQL，而是 Drizzle 的表定义代码。它做两件事：

  1. 描述结构：sqliteTable("users", {...}) 用 TS 对象声明"表叫什么、有哪些列、什么类型、谁当主键"。
  2. 生成迁移：跑 npm run db:generate，drizzle-kit 把 schema 和上一次的 schema 对比，差量生成 SQL 迁移文件写到 drizzle/。

迁移文件是数据库的"提交历史"：每个文件是一次 schema 变更，按顺序执行就能从空库一步步长成现在的结构。所以：

改表的标准流程：改 db/schema.ts → 跑 npm run db:generate → 人工检查新迁移文件 → 连同 schema 一起提交。禁止手写与 schema 不一致的 SQL——一切以 schema.ts 为唯一真相源。

运行时怎么拿到数据库连接？看 db/index.ts：

db/index.ts
import { drizzle } from "drizzle-orm/d1";
import * as schema from "./schema";

export async function getDb() {
  const { env } = await import("cloudflare:workers");
  if (!env.DB) {
    throw new Error(
      "Cloudflare D1 binding `DB` is unavailable. ..."
    );
  }

  return drizzle(env.DB, { schema });
}

getDb() 通过 Cloudflare 的 cloudflare:workers 模块拿到 env.DB 这个绑定（binding），再交给 Drizzle 包一层。之后代码里就能用接近 SQL、但由 TS 类型保护的写法查库。

类比（ORM = 类型安全的查询构造器）：直接用 SQL 字符串写查询，就像用 sprintf 拼 SQL——拼错了要到运行时才知道。Drizzle 用函数链（.select().from().where()）代替字符串拼接，编译器能帮你查错。

5精读 anime-selections/route.ts

这是"保存追番"的后端实现，整段读一遍。先看 GET（读列表）：

app/api/anime-selections/route.ts · GET
const validAnimeIds = new Set(allAnime.map(({ id }) => id));

export async function GET() {
  const user = await currentUser();
  if (!user) {
    return Response.json({ error: "Sign in required" }, { status: 401 });
  }

  try {
    const rows = await (await getDb())
      .select({ animeId: animeSelections.animeId })
      .from(animeSelections)
      .where(eq(animeSelections.userEmail, user.email));
    return Response.json({
      animeIds: filterKnownAnimeIds(rows.map(({ animeId }) => animeId), validAnimeIds),
    });
  } catch {
    return Response.json({ error: "Unable to load anime selections" }, { status: 500 });
  }
}
  • 第一行把 allAnime 里所有合法 id 装进 Set——这就是"白名单"。
  • 开头先 currentUser()（即 getSessionUser()），没登录就 401，绝不往下走。
  • 查询只查 user.email 自己的行——账号隔离，别人看不到你的追番。
  • 返回前再 filterKnownAnimeIds 过滤一遍：如果库里存着某部后来被删掉的番，它不会重新出现在你的列表里。

再看 PUT（保存列表）：

app/api/anime-selections/route.ts · PUT
export async function PUT(request: Request) {
  const user = await currentUser();
  if (!user) {
    return Response.json({ error: "Sign in required" }, { status: 401 });
  }

  let animeIds: string[];
  try {
    const payload = (await request.json()) as { animeIds?: unknown };
    animeIds = filterKnownAnimeIds(payload.animeIds, validAnimeIds);
  } catch (error) {
    const message = error instanceof Error ? error.message : "Invalid animeIds";
    return Response.json({ error: message }, { status: 400 });
  }

  try {
    const db = await getDb();
    await db.batch([
      db.delete(animeSelections).where(eq(animeSelections.userEmail, user.email)),
      ...selectionInsertBatches(animeIds).map((batch: string[]) =>
        db.insert(animeSelections).values(batch.map((animeId) => ({ userEmail: user.email, animeId }))),
      ),
    ]);
    return Response.json({ animeIds });
  } catch {
    return Response.json({ error: "Unable to save anime selections" }, { status: 500 });
  }
}
  • 白名单 + 去重：filterKnownAnimeIds 既丢掉未知 id，也 [...new Set(value)] 去重。
  • 整表替换：db.delete(...) 先删掉该用户旧列表，再插入新列表。
  • 原子提交：删除和所有插入批次都塞进同一个 db.batch()。要么全成功，要么全失败。

分批逻辑在 lib/anime-selections.js：

lib/anime-selections.js · selectionInsertBatches
export function selectionInsertBatches(animeIds) {
  return Array.from({ length: Math.ceil(animeIds.length / 50) }, (_, index) =>
    animeIds.slice(index * 50, (index + 1) * 50),
  );
}
为什么每批最多 50 条：D1 单条 SQL 语句最多绑定 100 个参数。每条追番记录要绑定 email + animeId 两个参数，所以一批最多 100 ÷ 2 = 50 条。超过就拆成多批。
为什么必须同一个 db.batch()："先删后插"分两次做，如果中间插入失败，就会清空用户原有追番。这像银行转账：不能"先扣钱再打款"分两步——扣完钱、打款失败，钱就丢了。放进同一个事务（batch）里，要么两步都成，要么一起回滚。

6精读 anime-episode-views/route.ts

已看标记和追番几乎同构：同样先认证、同样写 D1。区别在于校验更严，因为单集标记是精细数据，且要兼容旧版"连播范围"记录。

先看纯函数校验链（在 lib/anime-episode-views.js）：

lib/anime-episode-views.js · validateEpisodeView（单条校验）
export function validateEpisodeView(value, animeById) {
  if (!value || typeof value !== "object") {
    throw new TypeError("watched episode must be an object");
  }

  const { animeId, episodeStart, episode } = value;
  if (typeof animeId !== "string") {
    throw new TypeError("animeId must be a string");
  }

  const anime = animeById.get(animeId);
  if (!anime) {
    throw new RangeError("Unknown anime ID: " + animeId);
  }
  if (
    !Number.isInteger(episodeStart) ||
    !Number.isInteger(episode) ||
    episodeStart < 1 ||
    episode < episodeStart ||
    episode > anime.episodeCount ||
    episodeStart !== episode
  ) {
    throw new RangeError("Invalid episode range");
  }

  return { animeId, episodeStart, episode };
}

校验链（validateEpisodeViewBatch 循环调用上面的单条校验）一共挡住这些非法输入：

  • animeId 必须在 allAnime 里（白名单）。
  • 必须是单集：episodeStart === episode（旧版允许 start < episode 的连播范围，新版只收单集）。
  • 范围合法：1 ≤ episode ≤ anime.episodeCount。
  • 去重（同 key 只保留一条），且一批最多 25 条。

再看 route.ts 的 PUT 核心：

app/api/anime-episode-views/route.ts · PUT（标记已看）
export async function PUT(request: Request) {
  const user = await getSessionUser();
  if (!user) return Response.json({ error: "Sign in required" }, { status: 401 });

  let watchedEpisodes: { animeId: string; episodeStart: number; episode: number }[];
  let watched: boolean;
  try {
    const payload = (await request.json()) as { watchedEpisodes?: unknown; watched?: unknown };
    watchedEpisodes = validateEpisodeViewBatch(payload.watchedEpisodes, animeById);
    if (typeof payload.watched !== "boolean") throw new TypeError("watched must be a boolean");
    watched = payload.watched;
  } catch (error) {
    const message = error instanceof Error ? error.message : "Invalid watched episode";
    return Response.json({ error: message }, { status: 400 });
  }

  try {
    const db = await getDb();
    if (watched) {
      await db.batch([
        db
          .insert(animeEpisodeViews)
          .values(
            watchedEpisodes.map((watchedEpisode) => ({ userEmail: user.email, ...watchedEpisode })),
          )
          .onConflictDoNothing(),
      ]);
    }
    // watched === false 时：按主键逐条 delete（代码略）
    return Response.json({ watchedEpisodes, watched });
  } catch {
    return Response.json({ error: "Unable to save watched episode" }, { status: 500 });
  }
}
  • onConflictDoNothing()：主键冲突（这条已看过）就跳过不报错——这就是"幂等"，同一请求发两遍结果一样，不会产生重复行。
  • watched === false 时走删除分支（源码里 deleteWatchedEpisode 按主键四列逐条删），这里省略。
  • 返回体只回显服务器实际认可的值，不信任浏览器给的身份——userEmail 始终来自会话，不是请求体。

GET 里还有个"历史包袱"处理：旧版本允许把"连播范围"（比如 episodeStart: 1, episode: 3）存成一行。读取时，isLegacyEpisodeViewForAnime 认出这些旧记录，用 episodeViewUnitsForRange 把它们展开成单集，写回一批单集记录，并删掉旧的范围行——一次读取就把老数据原地迁移成新格式。这些纯函数都在 lib/anime-episode-views.js，route.ts 只是调用它们。

为什么"写入幂等"很重要：网络不可靠，浏览器可能重发同一个请求。幂等保证重发不会把"已看"写坏。这跟竞赛里"重复提交同一答案不会改变结果"是一个道理。

7HTTP 状态码 + 本地开发数据库

后端和浏览器之间靠状态码沟通"结果如何"。本项目用到的状态码：

状态码含义本项目哪里用
200成功读取、保存、标记成功
201创建成功注册新账号
400请求参数不合法body 不是合法 JSON、id 不在白名单、集数越界
401未登录 / 凭据错误getSessionUser() 返回 null
409冲突注册时邮箱已被占用
500服务器内部错误数据库读写异常等 catch 分支

响应格式全站统一：Response.json({ ... }, { status })——第一个参数是 JSON 对象，第二个参数指定状态码。

8本章测验

1. PUT 保存追番时，为什么 delete 旧列表和 insert 新列表必须放进同一个 db.batch()？

db.batch() 是一个事务：要么全部执行，要么全部回滚。若"先删后插"分成两次独立提交，中途插入失败就会留下"已删光、没插进去"的空列表。类比银行转账：不能先扣钱再打款分两步。

2.（多选）浏览器发来请求后，API 端必须先做的检查/处理有哪些？

A、B、C 都是必须的。D 是错的：用户身份只能来自服务端会话（getSessionUser()），绝不信浏览器传来的邮箱——否则任何人都能伪造请求读写别人的追番。这是"账号隔离"的根基。

3. 追番插入为什么要按每批最多 50 条分批（selectionInsertBatches）？

D1 对单条 SQL 的绑定参数有 100 个的上限。每条追番记录绑定 email 和 animeId 两个参数，因此一批最多 100 ÷ 2 = 50 条。selectionInsertBatches 用 Math.ceil(n / 50) 算出批数，逐批 slice。
