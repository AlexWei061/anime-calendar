维护手册 SOP：每次改动都按流程走

前九章让你「看得懂」这个项目，这一章开始让你「改得动、改不坏」。维护一个已经能跑的网站，最怕的不是不会写，而是改错地方、改出副作用、忘了验证。本章把最常见的七类维护任务写成标准操作流程（SOP），照着走就不会翻车。

实战手册 前置：第 01～09 章 改代码前必读 AGENTS.md 配套：第 11 章修 bug

1通用流程 + 模块地图：先想清楚，再动手

维护一个运行中的网站，和维护一个已经 AC 的算法程序是同一件事：改一行可能让别处 WA。竞赛里你有「提交前 checklist」（数组越界？爆 int？边界 case？），维护项目也要有——这就是 SOP。任何改动，哪怕是改一个错别字，都先过一遍下面的六步：

  1. 明确目标：要改什么？用户在界面上能看到什么变化？像写题前先读题，把「验收标准」写下来，比如「7 月番里《×××》的首播日期从 7 月 5 日改成 7 月 4 日」。
  2. 找到文件：按下方的模块地图定位。界面在 app/page.tsx，样式在 app/globals.css，算法在 lib/，数据在 data/，接口在 app/api/，数据库表在 db/schema.ts。
  3. 最小修改：只改与目标直接相关的文件。不要顺手重构、格式化大文件、升级依赖——外科手术式修改，切开就缝上。
  4. 更新相关测试断言：改了目录/时间/集数/封面，就同步改 tests/ 里对应的断言；否则 npm test 会立刻报警。
  5. 验证：跑 npm run lint -- --ignore-pattern .worktrees 和 npm test，全绿才算完。
  6. git 提交：一条说清「改了什么、为什么」的提交信息。不要一个提交里塞进两件不相干的事。
类比：这套流程就是竞赛里的「审题 → 想算法 → 写代码 → 造数据对拍 → 提交」。跳过第 4、5 步直接改代码，等于写完不测就交——WA 了都不知道错在哪一步。

2任务①改文案/样式 & 任务②修一条番剧数据

任务① 改文案或界面样式

何时做：改一句说明文字、调一个颜色、微调卡片尺寸。涉及文件：app/page.tsx（文案与结构）+ app/globals.css（样式）。

  1. 打开 app/page.tsx，找到那句文案所在的 JSX，改成新文案。
  2. 若要改颜色，去 app/globals.css 顶部的 :root 找对应 token（--accent、--accent-2、--paper 等），改它的值。
  3. 同名的 token 在 :root[data-theme="dark"] 里也有一份，必须同步改。
  4. 改完用右下角浮动按钮切两套主题各看一遍，再缩到 ≤860px 看移动端。
铁律：颜色只能通过 :root 里的设计 token 消费，禁止在任何组件规则里写硬编码色值（#ff0000、rgb(...) 都不行）。因为全站是「亮色樱花粉彩 + 暗色霓虹夜色」双主题，暗色是 :root[data-theme="dark"] 里同名 token 覆盖实现的——你在组件里写死一个颜色，深色模式下它就赖着不换了。
风险点：最容易翻车的是「只改了亮色忘了暗色」或「图省事在组件里写死色值」。改完务必把两套主题、桌面和移动端各看一遍。

任务② 修一条番剧数据

何时做：某部番的标题、集数、首播日期、周几、时刻写错了。涉及文件：季度目录文件 + 对应测试。

  1. 找到所属季度目录：2026-07 番在 data/anime.js 的 yucAnime 数组里；历史季度在 data/yuc-history-<year>.js 里。
  2. 改对应的字段（titleZh、episodeCount、premiereDateBeijing、scheduleWeekday、beijingTime 等）。
  3. 核对该季度 catalogCount === anime.length：加了部番要把 catalogCount +1，删了要 -1。
  4. 更新 tests/anime-data.test.mjs 里相关断言（它明确断言 catalogCount、每部番的字段完整性、关键番剧的 ID 存在与否）。
  5. 跑 npm test。

以 2026-07 的季度入口为例，这个对象就是「目录元信息」，catalogCount 和 anime.length 必须一致：

data/anime.js 季度元信息（真实代码）
export const season = {
  "label": "2026 年 7 月番",
  "timeZoneLabel": "北京时间（UTC+8）",
  "updatedAt": "2026-07-16",
  "catalogCount": 66,
  "sourceName": "YUC 2026年7月新番表",
  "sourceUrl": "https://yuc.wiki/202607/"
};
风险点：每个 id 必须稳定且全局唯一，不能用标题当身份标识（标题会撞名、会改）。历史季度文件是脚本生成的，不要手改——7 月番才允许直接改 data/anime.js。

3任务③新增/更新封面 & 任务④维护 2026-07 YUC 目录

任务③ 新增或更新一张封面

何时做：某部番的封面裂了、换新图、或新增一部番需要封面。涉及文件：封面图片 + data/anime.js 里的 coverUrl/coverAlt。

  1. 下载原始图片到本地中间目录。
  2. 跑 npm run convert:covers-webp：把独立封面无损转成 WebP，并同步目录里的逻辑封面路径。
  3. 跑 npm run generate:cover-sprites：把全部 WebP 打成 4×10、quality 90 的网格图集，生成映射并移除已打包的独立文件。
  4. 更新条目里的 coverUrl（稳定逻辑封面键，7 月用稳定 slug）和 coverAlt（无障碍替代文本）。
  5. 跑 npm test（里面有断言会检查每张封面都映射到图集、图集体积和文件数不超预算）。
铁律：禁止手编 data/cover-sprites.js 和图集文件。运行时封面由映射文件指到 public/covers/yuc/sprites/ 的 4×10 图集；顺序必须「先转 WebP，再打图集」，倒过来或跳过一步，页面就裂图或映射对不上。

任务④ 维护 2026-07 YUC 目录（先行排期）

何时做：7 月番里出现「M/D先行N话」这种特殊排期。涉及文件：data/anime.js 的 yucAnime。

  1. 同时核对 YUC 周表和作品详情里的 broadcast_r 字段。
  2. 若详情写有「M/D先行N话」及之后的固定周播，必须写四个字段：premiereDateBeijing、premiereKind: "network"、premiereEpisodeCount、regularBroadcastStartDateBeijing。
  3. 没有明确时刻的网络首播，beijingTime 必须留 null（页面会放进「网络配信 · 时刻未定」区域），禁止虚构时间。
  4. 凌晨 00:00～04:59 的节目，交给 lib/calendar.js 自动归到前一天显示「次日 HH:MM」，别在页面里手工挪日期。

真实例子——《躲在超市后门抽烟的两人》就是「6/3 先行 6 话 + 7/9 起固定周播」：

data/anime.js 先行 N 话的完整字段（真实代码，省略无关行）
{
  "id": "super-yani",
  "episodeCount": 12,
  "titleZh": "躲在超市后门抽烟的两人",
  "premiereDateBeijing": "2026-06-03",
  "premiereEpisodeCount": 6,
  "regularBroadcastStartDateBeijing": "2026-07-09",
  "premiereKind": "network",
  "scheduleWeekday": "Thu",
  "beijingTime": "22:56",
  "station": "YUC 周表"
}

对应地，lib/calendar.js 里的 formatBroadcastTime 负责把 24 点后的时间显示成「次日 HH:MM」：

lib/calendar.js formatBroadcastTime（真实代码）
export function formatBroadcastTime(time) {
  const minutes = timeToMinutes(time);
  if (minutes < 24 * 60) return time;

  const nextDayMinutes = minutes - 24 * 60;
  return `次日 ${String(Math.floor(nextDayMinutes / 60)).padStart(2, "0")}:${String(
    nextDayMinutes % 60,
  ).padStart(2, "0")}`;
}

而「凌晨归前一天」的日期挪移发生在 layoutBroadcast——00:00～04:59 会被算进前一天，时间加 24 小时显示：

lib/calendar.js layoutBroadcast（真实代码，省略无关行）
function layoutBroadcast(broadcastDate, broadcastTime) {
  const minutes = timeToMinutes(broadcastTime);

  if (minutes < 5 * 60) {
    return {
      date: addDays(broadcastDate, -1),
      time: formatTime(minutes + 24 * 60),
      broadcastDate,
      broadcastTime,
    };
  }

  return { date: broadcastDate, time: broadcastTime, broadcastDate, broadcastTime };
}
风险点：先行段是第 1 至 N 集，固定周播从第 N+1 集开始；不能把先行集数塞进之后的电视时段，也不能给「时刻未定」的网络首播编一个假时刻。这组字段一旦写错，tests/calendar.test.mjs 里的先行+周播断言会直接红给你看。

4任务⑤重新生成历史数据 & 任务⑥改数据库表结构

任务⑤ 重新生成历史数据

何时做：某一历史季度的排期要整体刷新。涉及文件：data/anilist-*.js、data/yuc-history-*.js、data/syoboi-history-*.js。

顺序不能乱：只更新 AniList/YUC 目录时，先跑 AniList 再生成历史目录；重新核对电视排期时，顺序必须是 AniList → YUC 目录 → しょぼい快照 → 再生成 YUC 目录，才能把新快照合并回最终目录。
  1. npm run generate:anilist-pilot：拉取 AniList 首播、时刻与集数。
  2. npm run generate:yuc-history-pilot：合并 YUC 中文名/封面 + AniList 排期 + 已有しょぼい快照，生成历史目录。
  3. npm run generate:syoboi-history：按当前目录抓取しょぼい电视排期，生成快照。
  4. 再跑一次 npm run generate:yuc-history-pilot，把新快照合并回目录。
  5. 跑 npm test。
铁律：生成结果一律不手编。字段合并优先级是 YUC → AniList → しょぼいカレンダー → 估算或 null，低优先级来源只能补空值、不能覆盖已有值；并保留 sourceUrl 和 season.updatedAt 的审计价值，别为了「干净」把它们删了。

任务⑥ 改数据库表结构

何时做：要加新字段/新表（比如给已看加一列）。涉及文件：db/schema.ts + drizzle/ 迁移。

  1. 改 db/schema.ts：用 Drizzle 的 sqliteTable 定义或调整表。
  2. 跑 npm run db:generate：让 Drizzle 生成新迁移。
  3. 检查 drizzle/ 下新生成的迁移文件，确认 SQL 与你预期一致。
  4. 把 db/schema.ts 和新迁移一起提交。
db/schema.ts 追番表定义（真实代码）
import { integer, primaryKey, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const animeSelections = sqliteTable(
  "anime_selections",
  {
    userEmail: text("user_email").notNull(),
    animeId: text("anime_id").notNull(),
  },
  (table) => [primaryKey({ columns: [table.userEmail, table.animeId] })],
);
铁律：禁止手写与 schema 不一致的 SQL。还要保持 .openai/hosting.json 里的 d1: "DB" 与 getDb() 使用的 DB 绑定一致，别把真实资源 ID、密钥写进仓库。

5任务⑦发布上线 & 红绿灯表

任务⑦ 发布上线

  1. npm test 全绿（它 = 类型检查 + 构建 + 跑测试）。
  2. 提交到 main，推送到 GitHub。
  3. 触发 Sites 部署。默认保持私有访问，只有用户明确要求公开时才调可见范围。
  4. 以部署状态为准：确认部署成功再交付 URL。
风险点：如果远端仓库有并发更新（别人先推了新提交），先合并、再验证、绝不强推覆盖对方改动。发布前保留生成好的图集和 data/cover-sprites.js，别把已打包的封面还原成一大堆独立静态文件（会超 Sites 静态文件承载上限）。

类比：绿灯区是你「手写的源代码」，红灯区是「编译产物 / 生成数据」。就像 C++ 里你会改 .cpp 却不会去改 .o、.exe——改生成物，下次一重新生成就被覆盖，等于白改还引入不一致。

6每次改动后的通用检查清单

无论做了什么改动，提交前过一遍这张清单（就像竞赛交卷前过一遍自己的对拍结果）：

检查项怎么验证
类型检查过npm run typecheck 无输出报错
Lint 过npm run lint -- --ignore-pattern .worktrees 无报错
测试全绿npm test（类型检查 + 构建 + tests/*.test.mjs 全过）
两套主题都正常右下角按钮切亮/暗，各看一眼改动处
≤860px 移动端正常缩窄窗口，单日议程和选择器还在
路由后退正常点进 ?page=search / ?page=mine 后浏览器后退/前进能回来
数据改动后目录数一致catalogCount === anime.length，npm test 不报警
封面改动后图集已重生成确认跑过 convert:covers-webp + generate:cover-sprites，图集映射对得上
口诀：改完一定「类型 + lint + test + 两套主题 + 移动端」五连查。少了任何一项，都可能把一个能用的站改成半残。

本章核心术语

SOP Standard Operating Procedure
标准操作流程：把高频任务固化成固定步骤，避免每次凭记忆现想、漏步骤。
设计 token
app/globals.css 的 :root 里定义的 CSS 变量（如 --accent），亮暗两套主题各一份，组件只消费变量、不写死颜色。
封面图集 sprite
把大量小图拼成一张 4×10 大图 + 坐标映射，减少部署文件数量。由脚本生成，禁手编。
先行排期
「M/D 先行 N 话 + 后续固定周播」：前 N 集一次性放出，之后每周一集。需要四个字段精确描述。
审计字段
sourceUrl、updatedAt、*Source 这类记录「数据从哪来、何时更新」的字段，保留它们才能追溯数据源头。

7本章测验

1.（多选）以下哪些文件/目录「禁止手工编辑」？

历史目录、しょぼい快照、AniList 原始资料、图集映射、D1 迁移，都是「生成物」——它们要么由脚本重新生成，要么由工具生成，手改后一旦重跑就会被覆盖，还会引入不一致。而 app/page.tsx 和 lib/calendar.js 是你手写的源码，是绿灯区，可以改。

2.（单选）某部 2026-07 番的 YUC 详情写「7/5 先行 3 话」+ 之后固定周播，必须写哪组字段？

先行段（第 1 至 N 集）靠 premiereDateBeijing + premiereKind:"network" + premiereEpisodeCount 定位，后续固定周播从第 N+1 集开始、靠 regularBroadcastStartDateBeijing 定位。四个缺一不可；没有明确时刻时 beijingTime 还要留 null，不能虚构。

3.（单选）新增/更新一张封面，正确的操作顺序是？

必须「先无损转 WebP，再打 4×10 图集」——图集脚本读的是 WebP 中间产物，顺序倒了会映射错位。图集映射和 data/cover-sprites.js 都不能手编，最后跑 npm test 让「每张封面都映射到图集」的断言帮你兜底。
