账号与会话安全：网站凭什么认得你

上一章你知道数据怎么存进 D1。这一章解决真正要害的问题：存进去的东西，凭什么只能被它的主人读到、别人偷不走。用竞赛的话说，这一整章就是在解一道 OJ 题——"如何在不泄露密码的前提下验证密码"。

1威胁模型：两个问题，三个敌人

一个带登录的网站，每时每刻都在回答两个问题：

  • 你是谁？——认证（authentication）。用户自称是 alex@example.com，怎么证明他真的持有这个账号？
  • 你现在还是你吗？——会话（session）。用户刚才登录过，之后一连串请求，怎么知道每一个还是同一个人、而且登录没过期？
类比：认证像进考场时查验身份证——一次性、相对昂贵、要拿出真凭实据；会话像老师发给你贴在桌上的"已签到"便签——之后你起身去厕所再回来，不用再掏身份证，亮一下便签就行。便签被人偷走或伪造，就是"会话劫持"。

要做安全设计，先列出敌人。这个项目要防的三个攻击者：

敌人它干什么对策（对应后文）
偷看流量（窃听者 / 中间人）在公共 WiFi 上抓包，截获你发出去的明文密码或房卡HTTPS 加密传输；Cookie 加 Secure
伪造身份（冒充者）不偷看，直接假装成你，往服务器发"我是 alex"的请求密码校验；会话 token 足够随机、无法猜中
数据库泄露（拖库）把整个数据库文件偷走密码只存哈希、会话只存 token 的哈希
认证 authentication
验证"你是谁"。本项目靠邮箱 + 密码。
会话 session
登录后保持"你还是你"的一段有效状态。本项目靠 ac_session Cookie + auth_sessions 表。
哈希 hash
把任意长度输入变成定长"指纹"的单向函数，见下一节。
明文 / 密文 plaintext / ciphertext
能直接读的原样数据 vs 经过变换的数据。数据库里不允许出现密码或 token 的明文。
安全设计的铁律：这三个敌人不是三选一，而是会叠加。正确的姿势是假设最坏情况已经发生——数据库已经被偷了——然后去设计"就算拖库，攻击者也拿不到能直接登录的东西"。下文所有机制都围绕这一条展开。

2密码存储：为什么明文是灾难

新手最容易犯的错：把密码原样存进 users 表。后果是——数据库一旦泄露，所有用户的邮箱和密码一起裸奔；而大多数人好几个网站共用同一个密码，等于其他网站也一起沦陷。所以数据库里永远不能出现明文密码。

哈希：单向函数，只能正着算

哈希函数把任意长度的输入变成固定长度的"指纹"，关键是单向：正着算极快，逆着算（从指纹反推原文）在计算上不可行。

类比：搅拌机——把一堆水果打成泥只要几秒，但你想从果泥还原出"原本有几颗草莓、几片香蕉"是不可能的。或者更数学一点：把两个大质数相乘很快（1009 × 1013 一秒钟出答案），但把乘积 1022117 做因数分解却没有高效算法——这正是 RSA 加密的地基。哈希同理：从密码算哈希容易，从哈希反推密码只能暴力试。

加盐：两个人都设 "12345678"，哈希也不同

如果只做哈希，密码相同则哈希相同，攻击者一眼能看出哪些人用了同一个弱密码；还能用彩虹表（预先算好"常见密码 → 哈希"的对照表）直接反查。解法：注册时给每个用户随机生成一段盐 salt，把"盐 + 密码"一起哈希。盐就公开存在哈希串里，但因为人人不同，同一个密码在不同用户手里得到不同哈希，彩虹表也废了。

PBKDF2 迭代 10 万次 = 故意变慢

普通哈希（如 SHA-256）追求快；密码哈希却故意要慢：把"密码 → 密钥"这个过程重复跑 10 万次。正常登录一次只多花几十毫秒，用户无感；但暴力破解要试几百万个候选密码，每个都慢 10 万倍，直接拖垮攻击者。

lib/auth.js 密码哈希与校验（节选）
const PBKDF2_ITERATIONS = 100000;
const SALT_BYTES = 16;
const KEY_BYTES = 32;
const SESSION_TOKEN_BYTES = 32;

export async function hashPassword(password, salt = crypto.getRandomValues(new Uint8Array(SALT_BYTES))) {
  const key = await derivePasswordKey(password, salt, PBKDF2_ITERATIONS);
  return `pbkdf2$${PBKDF2_ITERATIONS}$${toHex(salt)}$${toHex(key)}`;
}

export async function verifyPassword(password, stored) {
  if (typeof stored !== "string") return false;
  const parts = stored.split("$");
  if (parts.length !== 4 || parts[0] !== "pbkdf2") return false;
  const iterations = Number.parseInt(parts[1], 10);
  if (!Number.isInteger(iterations) || iterations <= 0) return false;
  const salt = fromHex(parts[2]);
  const expected = fromHex(parts[3]);
  if (!salt || !expected || expected.length !== KEY_BYTES) return false;
  const actual = await derivePasswordKey(password, salt, iterations);
  return constantTimeEqual(actual, expected);
}

逐行读 hashPassword：

  • salt = crypto.getRandomValues(new Uint8Array(16))：生成 16 字节随机盐。注意用的是 Crypto API 的密码学安全随机源，不是 Math.random()（后者可预测，不能用来生成盐或 token）。
  • derivePasswordKey(password, salt, 100000)：PBKDF2 跑 10 万次，输出 32 字节密钥。
  • 返回值是 pbkdf2$100000$<盐hex>$<密钥hex> 四段拼起来：自描述。将来改迭代次数，旧哈希也能被正确验证——因为参数都写在哈希串里了。

再读 verifyPassword：先用 $ 拆成四段，逐项校验"前缀、段数、迭代次数、盐/密钥长度"，任何一项不合法直接 false（防御畸形输入）；然后用存着的盐和迭代次数重新派生一遍，交给 constantTimeEqual 比较。核心思想：验证 = 用相同配方重算一遍再比对。

lib/auth.js 常量时间比较（防时序侧信道）
function constantTimeEqual(a, b) {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let index = 0; index < a.length; index += 1) {
    diff |= a[index] ^ b[index];
  }
  return diff === 0;
}

为什么不用 a[i] === b[i] 那样"第一个不同的地方就 return"？因为那种短路比较的耗时随"相同前缀长度"变长。攻击者测量响应时间，就能一个字节一个字节地逼近真实哈希——这叫时序侧信道。而 constantTimeEqual 无论哪一位不同，都老老实实遍历完所有字节，用时与内容无关，不泄露任何前缀信息。

竞赛老朋友：diff |= a[index] ^ b[index] 就是"异或"——相同为 0、不同为 1，最后 diff === 0 表示逐位全同。这是用位运算在一次遍历里统计差异的经典套路，和你写过的判重、找唯一元素一脉相承。

3会话：登录之后，凭什么还认得你

HTTP 是无状态的：服务器处理完一个请求就"失忆"了，下一个请求它根本不知道和上一个是不是同一个人。所以要靠会话把这几个请求串起来。本项目的做法是"房卡"：

房卡模型：登录成功，前台（服务器）给你一张写着随机长串数字的房卡（token）。之后你每次进房门（发请求）都出示房卡。前台不保存房卡的明文，只存了房卡的"指纹"（哈希）；你出示时它现算指纹对一下，对上了且没过期才放行。这样即使指纹库被偷，攻击者也没法从指纹造出能过闸的房卡。
  1. 登录 / 注册成功 → createSession：generateSessionToken() 生成 32 字节随机 token（64 个十六进制字符）。
  2. 明文 token 通过 Set-Cookie 发给浏览器；浏览器自动保存，并在之后的每个请求里自动带回。
  3. 服务端只把 token 的 SHA-256 哈希 + 邮箱 + 过期时间存进 auth_sessions 表。
  4. 之后每个请求：从 Cookie 头里取出 token → 再哈希一次 → 查表 → 命中且未过期，才认定登录。
lib/auth.js 会话令牌的生成与哈希
export function generateSessionToken() {
  return toHex(crypto.getRandomValues(new Uint8Array(SESSION_TOKEN_BYTES)));
}

export async function hashSessionToken(token) {
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(token));
  return toHex(new Uint8Array(digest));
}
app/auth.ts 签发、校验、销毁会话
export const SESSION_COOKIE = "ac_session";
const SESSION_MAX_AGE_SECONDS = 30 * 24 * 60 * 60;

export async function getSessionUser(): Promise<SessionUser | null> {
  const token = readSessionToken(await headers());
  if (!token) return null;

  const tokenHash = await hashSessionToken(token);
  const db = await getDb();
  const rows = await db
    .select({
      email: users.email,
      displayName: users.displayName,
      avatarVersion: users.avatarVersion,
      expiresAt: authSessions.expiresAt,
    })
    .from(authSessions)
    .innerJoin(users, eq(authSessions.userEmail, users.email))
    .where(eq(authSessions.tokenHash, tokenHash));
  const row = rows[0];
  if (!row) return null;
  if (row.expiresAt <= Date.now()) {
    await db.delete(authSessions).where(eq(authSessions.tokenHash, tokenHash));
    return null;
  }
  return {
    email: row.email,
    displayName: row.displayName,
    avatarVersion: row.avatarVersion,
    avatarUrl: avatarUrl(row.avatarVersion),
  };
}

export async function createSession(userEmail: string, requestUrl: string): Promise<string> {
  const token = generateSessionToken();
  const tokenHash = await hashSessionToken(token);
  const expiresAt = Date.now() + SESSION_MAX_AGE_SECONDS * 1000;
  await (await getDb()).insert(authSessions).values({ tokenHash, userEmail, expiresAt });
  return `${SESSION_COOKIE}=${token}; ${sessionCookieAttributes(requestUrl, SESSION_MAX_AGE_SECONDS)}`;
}

export async function destroySession(requestUrl: string): Promise<string> {
  const token = readSessionToken(await headers());
  if (token) {
    const tokenHash = await hashSessionToken(token);
    await (await getDb()).delete(authSessions).where(eq(authSessions.tokenHash, tokenHash));
  }
  return expiredSessionCookie(requestUrl);
}

读 getSessionUser，这是全站最关键的几行：

  • readSessionToken(await headers())：从请求头里解析出名为 ac_session 的 Cookie 值；没有就 null。
  • hashSessionToken(token)：拿到明文 token 后立刻再哈希——注意服务端全程不把明文 token 写进数据库。
  • 联表查询 auth_sessions join users，按 tokenHash 匹配。
  • 没查到 → null；查到但已过期 → 顺手删掉这条会话（懒清理）再返回 null。
  • 命中且未过期 → 返回 { email, displayName, avatarUrl }。这三样才是"你是谁"的权威答案。
两处哈希，用途不同：密码是用户自己选的低熵字符串，容易被猜，所以用 PBKDF2 迭代 10 万次拖慢；token 是随机生成、本身不可猜的高熵值，用"快"的 SHA-256 就足够。这是理解"为什么密码和 token 哈希算法不一样"的关键。

4Cookie 的四个属性，各防一种攻击

Set-Cookie 字符串就是 sessionCookieAttributes 拼出来的：

lib/auth.js 会话 Cookie 属性
export function sessionCookieAttributes(requestUrl, maxAge) {
  const secureAttribute = new URL(requestUrl).protocol === "https:" ? " Secure;" : "";
  return `HttpOnly;${secureAttribute} SameSite=Lax; Path=/; Max-Age=${maxAge}`;
}
属性取值作用防什么
HttpOnly无值，写上即生效页面里的 JS 读不到这个 Cookie（document.cookie 拿不到它）XSS 注入后偷 Cookie
Secure无值，仅 HTTPS 请求加只在 HTTPS 请求里携带房卡，明文 HTTP 不泄露中间人窃听
SameSite=LaxLax跨站发起的请求不自动带 Cookie（顶级导航除外）CSRF 跨站伪造请求
Path=//全站所有路径都携带这个 Cookie保证任何页面 / API 都拿得到会话
Max-Age秒数（这里 30 天）Cookie 有效期，到期浏览器自动丢弃会话过期兜底

注意 Secure 前面的判断：new URL(requestUrl).protocol === "https:"。意思是只有 HTTPS 请求才加 Secure，HTTP 请求（比如本地 http://localhost 开发）不加——否则浏览器会因为"不安全连接却要求 Secure"而拒绝接收 Cookie，本地就登录不了了。线上走 HTTPS 自动加 Secure，本地 HTTP 自动跳过，两者兼容。

一句话分工：HttpOnly 防"别人在页面里偷"（XSS）；Secure 防"路上被偷听"（窃听）；SameSite=Lax 防"别的网站冒充你发请求"（CSRF）。这也是 tests/auth.test.mjs 里"session cookie is Secure only for HTTPS"那条测试在守护的行为。

5走读一条注册请求

把上面的零件串起来，看注册 API 的完整流程：

app/api/auth/register/route.ts 完整代码
import { eq } from "drizzle-orm";
import { getDb } from "../../../../db";
import { users } from "../../../../db/schema";
import {
  hashPassword,
  normalizeDisplayName,
  validateEmail,
  validatePassword,
} from "../../../../lib/auth.js";
import { createSession } from "../../../auth";

export async function POST(request: Request) {
  let email: string;
  let password: string;
  let displayName: string;
  try {
    const payload = (await request.json()) as {
      email?: unknown;
      password?: unknown;
      displayName?: unknown;
    };
    email = validateEmail(payload.email);
    password = validatePassword(payload.password);
    displayName = normalizeDisplayName(payload.displayName, email);
  } catch (error) {
    const message = error instanceof Error ? error.message : "Invalid registration";
    return Response.json({ error: message }, { status: 400 });
  }

  try {
    const db = await getDb();
    const existing = await db
      .select({ email: users.email })
      .from(users)
      .where(eq(users.email, email));
    if (existing.length > 0) {
      return Response.json({ error: "该邮箱已注册，请直接登录" }, { status: 409 });
    }

    const passwordHash = await hashPassword(password);
    await db.insert(users).values({ email, passwordHash, displayName, createdAt: Date.now() });
    const sessionCookie = await createSession(email, request.url);
    return Response.json(
      { email, displayName, avatarUrl: null },
      { status: 201, headers: { "Set-Cookie": sessionCookie } },
    );
  } catch {
    return Response.json({ error: "Unable to register" }, { status: 500 });
  }
}
  1. 校验输入（400）：第一个 try 里，validateEmail 校验邮箱格式、validatePassword 校验长度（8～72）、normalizeDisplayName 昵称为空时回退成邮箱。任何一个 throw 都进 catch 返回 400。
  2. 查重（409）：按邮箱查 users 表，已存在就返回 409 "该邮箱已注册，请直接登录"。
  3. 哈希入库：hashPassword 得到哈希串，插入 users。注意字段叫 passwordHash，明文密码从未落库。
  4. 签发会话：createSession(email, request.url) 返回一串 Set-Cookie。
  5. 返回 201：在响应头里带上 Set-Cookie，浏览器收到后自动存下房卡。
顺序很重要：必须先"校验"、再"查重"、最后"写库"。反过来会出事故：先写库再查重，重复注册就先插脏了数据；先查重但不校验邮箱格式，非法邮箱就被写进去了。每个状态码都在告诉前端"错在哪一层"。

状态码速记

状态码含义本项目里的例子
400 Bad Request输入不合法（格式 / 长度）邮箱格式错、密码太短
401 Unauthorized未登录 / 凭证无效登录密码错、数据 API 没会话
409 Conflict资源已存在（业务冲突）邮箱已注册
201 Created新建资源成功注册成功、用户已建
500 Internal Server Error服务器意外异常数据库挂了等
想一想：为什么注册成功返回 201 而不是 200？又为什么注册成功后还要顺手 createSession？（提示：注册即登录，用户建完账号立刻就是"已登录"状态，不用再跳去登录一次。）

6铁律：数据 API 的第一步永远是 getSessionUser()

浏览器是敌占区：用户可以改任何前端代码、用命令行手工发任意 HTTP 请求、伪造任意请求体。所以：

  • 用户身份只能来自服务端会话，不能来自请求体。看追番列表的 GET——它根本没有"接收邮箱参数"这个动作，邮箱是从 getSessionUser() 里查出来的。
  • 所有用户数据都挂在 userEmail 上（追番、已看、会话），账号隔离靠它。
  • 浏览器传来的东西只当"数据"，绝不当"身份"。
app/api/anime-selections/route.ts 每个数据 API 的开头（节选）
async function currentUser() {
  return getSessionUser();
}

export async function GET() {
  const user = await currentUser();
  if (!user) {
    return Response.json({ error: "Sign in required" }, { status: 401 });
  }
  // ... 之后用 user.email 查这个用户自己的追番列表
}

三条铁律：

  1. 每个数据 API 的第一行逻辑必须是 getSessionUser()；返回 null 立刻 401。
  2. 拿到 user 后，数据库查询全部用 user.email 做条件——邮箱不是请求参数，是会话里查出来的。
  3. 请求体（request.json()、query 参数）只用来传"要存什么数据"，永远不传"我是谁"。
如果有人提需求说"前端把邮箱发过来，后端直接用"，立刻拒绝。那等于让攻击者随便填别人的邮箱，就能读到、改掉别人的追番列表和已看记录。仓库里 tests/auth.test.mjs 有一条 doesNotMatch(/payload\.email|searchParams\.get\("email"\)/) 的断言，就是防止将来有人这么改的"哨兵测试"——它守在代码里，谁改了它测试就红。

7本章自测

1. 用户登录后，数据库 auth_sessions 表里存的是会话 token 的什么？

服务端只存 token 的 SHA-256 哈希（hashSessionToken）。这样即使数据库被拖库，攻击者拿到哈希也造不出能通过校验的房卡——因为哈希是单向的，他没法从指纹反推原文。

2.（多选）下面哪些是"Cookie 属性 → 它防的攻击"的正确配对？

HttpOnly 让 JS 读不到（防 XSS）、Secure 只在 HTTPS 携带（防窃听）、SameSite=Lax 阻止跨站自动带 Cookie（防 CSRF）。而 Path=/ 只决定 Cookie 在哪些路径生效，和"防拖库"无关——防拖库靠的是"只存哈希"。

3. 为什么密码哈希用 PBKDF2 还要迭代 10 万次？

迭代 10 万次是"故意变慢"：正常登录一次只多几十毫秒，用户无感；暴力破解要试几百万个候选密码，每个都慢 10 万倍，攻击成本被拉高到不可承受。长度由 KEY_BYTES = 32 决定，盐的随机性由 crypto.getRandomValues 保证，和迭代次数无关。
