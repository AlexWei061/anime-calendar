练习题与自测：像刷题一样上手

前面 11 章都是“读”。这一章是“做”。所有练习都在你本地电脑上进行，只要不 git push，就不会影响线上的任何人。做错也没关系——答案都折叠在题目下面。

阶段四 · 实战能力 约 1～2 小时 前置：第 01～11 章

1开始前的安全约定

  • 所有命令都在项目根目录（/Users/alex/Alex/anime-calendar）下执行；
  • 动手练习会改本地文件——做完记得改回来（答案里写了恢复方法），或者干脆先 git stash 留个后悔药；
  • 只有你想正式发布改动时才 git add + git commit + git push，练习不需要提交。
练习的正确姿势：先自己想 5 分钟，再动手试，最后对答案。直接看答案≈直接看题解，学不到东西。

2观察型练习：不动代码，只回答问题

练习 2-1：核对 2026 年 7 月季的 catalogCount

在项目根目录运行：

终端 用 Node 直接 import 数据文件
node -e "import('./data/anime.js').then(m => { const s = m.seasons.at(-1); console.log(s.id, s.label); console.log('catalogCount =', s.catalogCount, ' anime.length =', s.anime.length); })"
查看答案与讲解

输出应为 2026-july 2026 年 7 月番，且两个数字相等（66 = 66）。这一条是数据层的铁律：catalogCount 必须等于 anime.length，tests/anime-data.test.mjs 里专门有断言盯着它。以后每季度加完数据，第一件事就是核对这两个数。

练习 2-2：亲手验证“凌晨节目归前一天”

终端 调用 lib/calendar.js 的纯函数
node -e "import('./lib/calendar.js').then(m => { console.log(m.calendarDateForDateTime('2026-07-08', '01:30')); console.log(m.formatBroadcastTime('25:00')); console.log(m.startOfWeek('2026-07-12')); })"
查看答案与讲解

三行输出依次是：2026-07-07（周三凌晨 01:30 的节目归到周二栏目）、次日 01:00（25:00 的显示格式）、2026-07-06（周日所在周的周一）。这正是第 06 章讲的两个函数，现在你可以像跑竞赛程序一样直接调用它们——这就是“纯函数库”的好处。

练习 2-3：在数据里找到一部番并读出它的排期

终端 搜索数据文件
grep -n "sayonara-lara" data/anime.js
查看答案与讲解

打开 data/anime.js 对应的行，你能读出：id sayonara-lara、总集数 12、中文名“再见 拉拉”、首播 2026-07-05、周日（Sun）23:30、来源 YUC 周表。试着回答：它的第 3 集会显示在日历的哪一天几点？（2026-07-05 是周日，首播即周日 23:30；之后每周日 23:30 一集，第 3 集 = 07-19 周日。）

练习 2-4：让类型检查报一次错，再修好

暂时在 app/page.tsx 里随便找一行，把某个 useState("...") 的初始字符串改成数字（比如 useState(123)），然后运行 npm run typecheck，读一读报错；再把改动改回去，重跑确认全绿。

查看答案与讲解

你会看到类似 Type 'number' is not assignable to type 'string' 的报错，并精确指出文件:行:列。这就是第 09 章说的“编译期报错”：它在你运行网站之前就把类型错误抓出来。记住这个体验——以后看到 typecheck 报错不要慌，照它指的位置改就是了。

练习 2-5：在浏览器里当一次“侦探”

启动 npm run dev 打开网站，按 F12 打开开发者工具：① 在 Console 输入 2+3 回车；② 切到 Network 面板，点“我的番剧”页面，找到 anime-selections 请求，看它的状态码和响应；③ 切到 Application 面板，找 ac-theme 和 ac_session 两个键，说说它们分别是什么。

查看答案与讲解

① Console 就是 JS 的交互式解释器（≈Python REPL），应输出 5；② 未登录时该请求会返回 401（Sign in required），响应体是 JSON——你能亲眼看到第 07 章讲的认证流程；③ ac-theme 是主题选择（界面偏好），ac_session 是登录会话 Cookie（只有登录后才有，HttpOnly 所以 Console 读不到但 Application 面板能看见）。

3动手型练习：小步改，大步学

练习 3-1：改一处文案并本地验证

在 app/page.tsx 里找到页面顶部显示“播出表”或“番时表”的文案，把它改成“我的番剧日历”，保存后看 npm run dev 的页面是否热更新；确认后再改回来。

查看提示

搜 播出表 关键词定位。dev 模式下保存即生效（热更新），这就是“开发服务器”和“构建产物”的区别。改回来之后页面恢复原样即可，不用跑测试（纯文案不改逻辑），但正式提交前还是建议跑一次 npm test。

练习 3-2：给双主题动一次手术

在 app/globals.css 找到 :root 里的 --accent，把它临时改成一个夸张的颜色（比如 #00ff00），切深色模式看哪里变了；然后同样在 :root[data-theme="dark"] 里改对应的 --accent。观察两套主题各自生效，最后改回原值。

查看答案与讲解

你会发现：只改亮色的 token，切到暗色后颜色不变——因为暗色用自己的同名 token 覆盖。这就是“两套主题必须同时维护”的原因：token 名相同，值不同。练习里你只动了 --accent，而页面所有粉色都由它派生，一处改、处处变——这正是设计 token 的意义。

练习 3-3：故意改坏一个测试，看它怎么报警

打开 tests/calendar.test.mjs，找到断言 assert.equal(startOfWeek("2026-07-12"), "2026-07-06")，把右边的日期改成 "2026-07-05"，运行 node --test tests/calendar.test.mjs 看失败信息；然后改回原值重跑确认通过。

查看答案与讲解

你会看到红字 ✖ 和期望值/实际值的对照——这就是“回归测试”的报警方式。想想：如果这不是练习，而是你改代码改出来的失败，这个报错会精确告诉你哪个函数的行为变了。先写测试再修 bug 的流程，就是这个体验反过来：先让测试红，再改代码让它绿。

练习 3-4：往 2026-07 目录临时加一部“假番”，再删掉

在 data/anime.js 的 yucAnime 数组末尾复制一条现有记录，把 id 改成 test-anime-999、标题改成“测试番”，运行 npm test——观察哪个测试因为什么失败；然后把这条删掉重跑。

查看答案与讲解

大概率 tests/anime-data.test.mjs 会红：因为 catalogCount(66) 现在不等于 anime.length(67)。这一下你就亲身体会了数据校验是怎么工作的：不是有人盯着你，而是测试在盯着数据。修复方式不是改测试，而是把数据改对（删除假条目），并把 catalogCount 与条目数保持一致。

4模拟修 bug：三个真实风格的场景

每个场景给出症状和排查路线提示，答案给出完整推理链。这节最接近真实维护工作。

场景 A：“我的番剧”里某部番在日历上消失了

症状：用户反馈某部番在“播出表”正常，但加入追番后，“我的番剧”周历里看不到它。

排查路线提示

先确认这部番在“播出表”当前周有没有排期事件（可能本来就没有，比如它已完结、当前周不播）。再想“我的番剧”和“播出表”的数据源差异：前者是 allAnime 按 selectedAnimeIds 过滤，后者是全集。若两者同一周都该有事件，查这部番的字段是否缺失（scheduleWeekday / beijingTime 为空且不是网络放送，会被 eventsForWeek 跳过）。

查看完整推理链

① 在页面上把周切到该番首播周，看“播出表”是否显示——如果“播出表”也没有，问题在数据（字段缺失），不在追番逻辑；② 用练习 2-3 的 grep 找到该番记录，检查 scheduleWeekday/beijingTime 是否为 null——非网络番缺了它们就会被 eventsForWeek 的 if (!record.scheduleWeekday || !record.beijingTime) continue; 静默跳过；③ 若是网络番，确认它只出现在“网络配信·时刻未定”列表（dateOnlyEventsForWeek），不在时间轴上；④ 若数据没问题，再看 selectedAnimeIds 是否真包含它（保存接口白名单过滤）。绝大多数这类问题最终落在②：数据缺字段。

场景 B：一部 25:00 播出的番，显示在了“错误的一天”

症状：某番标称周六 25:00 播出，但用户在周六栏看不到、在周日栏看到了。

排查路线提示

回想第 06 章：25:00 = 次日 01:00，且凌晨节目按规则归到前一天。所以“周六 25:00”本来就该显示在周五栏（次日 01:00）……先别急着下结论，动手验证 calendarDateForDateTime 和 formatBroadcastTime 的实际输出。

查看完整推理链

① 用练习 2-2 的 node 命令验证规则本身（正确性基线）；② 核对数据里该番的 premiereDateBeijing 与 scheduleWeekday：数据若写“周六首播 25:00”，展开后事件会被 layoutBroadcast 归到周五栏——这不是 bug 而是规则；③ 真正要检查的是：数据来源（YUC）写的是“周五 25:00”还是“周六 25:00”？如果 YUC 周表把 25:00 标在周六，按行业习惯它指的就是“周五深夜播出”，需要在数据里写周五；④ 结论：先算后查，别在页面 JSX 里手动挪日期去“修复”——那会破坏所有共享这套规则的地方。

场景 C：追番列表保存后偶尔全部丢失

症状：用户追番列表很长（上百部），保存时有时成功、有时整个列表变空。

排查路线提示

打开 app/api/anime-selections/route.ts，找“先删后插”的代码。想想：如果删除成功、插入失败会怎样？什么样的列表会让插入失败？（提示：D1 单条语句最多 100 个绑定参数。）

查看完整推理链

① PUT 的语义是“整表替换”：先 delete 旧列表，再分批 insert 新列表；② 两者必须放在同一个 db.batch([...]) 里，D1 才保证原子性（要么全成功，要么全回滚）；③ 如果哪次修改把 delete 挪出了 batch（先删、单独插），插入中途失败就会留下“已删空”的数据库——列表就空了；④ 另一个易错点：每批最多 50 条（每条绑 email+animeId 两个参数，100÷2=50），分批逻辑在 lib/anime-selections.js 的 selectionInsertBatches；⑤ 修复/预防：永远保持“删 + 全部插入批”在同一个 batch 内，并给这段加一条回归测试。

加餐（选做）：给场景 C 写一条回归测试：构造一个“先删后插失败”的假数据库，断言保存失败后用户原有追番仍在。提示：参考 tests/anime-selection-storage.test.mjs 里已有的测试写法。

5结业自测

1.（多选）npm test 依次做了哪三件事？

脚本原文："test": "npm run typecheck && npm run build && node --test tests/*.test.mjs"。部署是单独的流程，不会随测试自动发生。

2.（单选）一部番“首日网络先行 3 话，之后每周固定播出”，数据里必须写哪组字段？

先行段是第 1～N 集（首播日放出），固定周播从第 N+1 集开始（regularBroadcastStartDateBeijing 那天起）。这四个字段缺一不可，tests/calendar.test.mjs 的“先行多集+后续周播”断言会同时检查：先行日集数范围正确、没有虚构时刻、首个固定周播日从下一集开始。拆成多条记录是错的——它是一部番。

3.（单选）D1 一条 SQL 语句最多能绑定多少个参数？追番保存因此每批最多插多少条？

上限 100；每条追番记录绑定（userEmail, animeId）两个参数 → 100÷2=50。所以 lib/anime-selections.js 的 selectionInsertBatches 按 50 分批。且所有批次必须和删除旧列表放进同一个 db.batch()，保证原子替换。
