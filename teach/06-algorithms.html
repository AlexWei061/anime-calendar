1先立规矩：这个项目怎么处理“日期”

Web 里处理日期有一万个坑（时区、夏令时、月份天数）。这个项目用了一个竞赛选手最顺手的办法：把日期一律当成 YYYY-MM-DD 字符串 + 整数运算，几乎不碰 Date 对象，所有计算都基于 UTC。

lib/calendar.js 第 1～20 行（真实代码）
function parseIsoDate(isoDate) {
  const match = /^(\d{4})-(\d{2})-(\d{2})$/.exec(isoDate);   // 正则校验格式
  if (!match) throw new RangeError(`Invalid ISO date: ${isoDate}`);

  const date = new Date(`${isoDate}T00:00:00Z`);             // 只按 UTC 解析
  if (Number.isNaN(date.getTime()) || date.toISOString().slice(0, 10) !== isoDate) {
    throw new RangeError(`Invalid ISO date: ${isoDate}`);    // 排除 2026-02-30 这类假日期
  }
  return date;
}

function formatIsoDate(date) {
  return date.toISOString().slice(0, 10);                    // 取回 YYYY-MM-DD
}

export function addDays(isoDate, days) {
  const date = parseIsoDate(isoDate);
  date.setUTCDate(date.getUTCDate() + days);                 // 只做天数加减
  return formatIsoDate(date);
}
  • “解析 → 运算 → 格式化”三步走，中间状态永远是 UTC 的 Date，绝不碰本地时区；
  • 输入不可信就抛异常（RangeError）——就像竞赛里的 assert，坏数据在第一时间炸出来，而不是静默算出错结果。

2经典取模题：算出某个日期所在周的周一

日历按“周一到周日”分栏，所以一切计算的起点是：给任意日期，求出它所在周的周一。

lib/calendar.js 第 38～46 行（真实代码）
export function startOfWeek(isoDate) {
  const date = parseIsoDate(isoDate);
  const mondayOffset = (date.getUTCDay() + 6) % 7;   // 0=周日 1=周一 ... 6=周六
  return addDays(isoDate, -mondayOffset);
}

export function weekDays(weekStart) {
  return Array.from({ length: 7 }, (_, offset) => addDays(weekStart, offset));
}

这里唯一的“算法”就是一行取模：getUTCDay() 返回 0～6（周日为 0），要换算成“距离周一有几天”，公式是 (day + 6) % 7。验证一下：周日 0 → (0+6)%7=6，往前退 6 天正好是周一；周三 3 → (3+6)%7=2，退 2 天是周一。✓

数学视角：整章你会发现，日历问题几乎都是模运算 + 等差数列。星期是模 7 的循环群，周播是公差为 7 的等差数列。把这个直觉装进脑子，下面所有代码都变得透明。

另一个用到“线性扫描 + 边界规则”的小函数是 seasonForWeek：季度按时间排序后从头扫，一旦某季度的“第一个完整周”开始日不晚于当前周，就把当前季度切换成它——等价于“找最后一个满足条件的区间”，O(n) 扫描即可。

3深夜动画的行业习惯：24:00 其实是次日 0 点

日本深夜动画常写“25:00 播出”——那其实是次日凌晨 1 点。这个项目的规则（写死在 AGENTS.md 里）：凌晨 00:00～04:59 的节目，在周历里归到前一天那一栏，显示成“次日 HH:MM”。

lib/calendar.js 第 115～142 行（真实代码）
export function formatBroadcastTime(time) {
  const minutes = timeToMinutes(time);
  if (minutes < 24 * 60) return time;            // 05:00～23:59 照常显示

  const nextDayMinutes = minutes - 24 * 60;
  return `次日 ${String(Math.floor(nextDayMinutes / 60)).padStart(2, "0")}:${String(
    nextDayMinutes % 60,
  ).padStart(2, "0")}`;                          // 24:00 → "次日 00:00"
}

function layoutBroadcast(broadcastDate, broadcastTime) {
  const minutes = timeToMinutes(broadcastTime);

  if (minutes < 5 * 60) {
    return {
      date: addDays(broadcastDate, -1),          // 关键：日期往前挪一天
      time: formatTime(minutes + 24 * 60),       // 01:30 → 25:30 显示用
      broadcastDate,
      broadcastTime,
    };
  }

  return { date: broadcastDate, time: broadcastTime, broadcastDate, broadcastTime };
}

拆开看：timeToMinutes("25:00") 就是 25*60+0 = 1500 分钟；1500 ≥ 1440，所以显示为 次日 01:00；而 layoutBroadcast 对 05:00 以前的节目把 date 减一天——于是“周三 01:30 播出的节目”会出现在周二那一栏，标注“次日 01:30”。

维护时最容易踩的坑：以后加数据，时间写 24:00、25:00 是合法且常见的（数据里真有不少）；但不要自己在页面 JSX 里手工把日期挪来挪去——所有挪动都必须经过 layoutBroadcast，否则会和新老代码打架。

4周历展开：从“首播信息”推导“每周播哪集”

这是全项目最核心的算法：数据里只存了“首播日期、星期几、时间、总集数”，但日历要展示的是每一周、每一天、每一集。来看 eventsForWeek 怎么展开：

lib/calendar.js 第 245～284 行（真实代码，节选）
export function eventsForWeek(records, weekStart) {
  const dates = new Set(weekDays(weekStart));          // 本周 7 天，O(1) 查表
  const events = [];

  for (const record of records) {
    // 有“逐段核实过的排期”就直接按段展开（2026-07 的先行连播等）
    if (record.episodeSchedules?.length) {
      events.push(...eventsFromEpisodeSchedules(record, dates));
      continue;
    }
    if (!record.scheduleWeekday || !record.beijingTime) continue; // 网络放送走另一条路

    const premiereEpisodeCount = record.premiereEpisodeCount ?? 1; // 首播几集，默认 1
    const firstScheduledEpisode = premiereEpisodeCount + (record.premiereKind === "network" ? 1 : 0);
    const scheduledWeekday = ["Sun","Mon","Tue","Wed","Thu","Fri","Sat"].indexOf(record.scheduleWeekday);
    const premiereWeekday = parseIsoDate(record.premiereDateBeijing).getUTCDay();
    const firstRegularBroadcastDate = record.regularBroadcastStartDateBeijing ??
      addDays(record.premiereDateBeijing, (scheduledWeekday - premiereWeekday + 7) % 7 || 7);

    for (let episode = firstScheduledEpisode; episode <= record.episodeCount; episode += 1) {
      const broadcastDate = episode === premiereEpisodeCount
        ? record.premiereDateBeijing
        : addDays(firstRegularBroadcastDate, (episode - premiereEpisodeCount - 1) * 7);
      const layout = layoutBroadcast(broadcastDate, record.beijingTime);
      if (!dates.has(layout.date)) continue;           // 不在本周就不生成
      events.push({ ...record, ...layout, episodeStart: episode === premiereEpisodeCount ? 1 : episode, episode });
    }
  }
  return events.sort(/* 按时间、再按 id 稳定排序 */);
}

里面藏着三个数学结构：

  • 模运算找“下一个目标星期几”：(scheduledWeekday - premiereWeekday + 7) % 7 || 7。若首播就是目标星期（差为 0），则 || 7 保证首次固定周播在下周同一天，而不是首播当天；
  • 等差数列展开每周集数：第 episode 集的播出日期 = 首播日 + (episode - 1) × 7 天——公差 7 的等差序列。代码里 (episode - premiereEpisodeCount - 1) * 7 就是把“先行 N 话占掉了 N 周”这个偏移扣掉；
  • Set 做 O(1) 剪枝：先算出本周 7 天放进 Set，每集的日期不在本周就直接跳过——不然要白算几百集的日期。

两种特殊排期也在这里分叉：

  • 先行 N 话（网络）：数据里写 premiereKind:"network" + premiereEpisodeCount:N + regularBroadcastStartDateBeijing（固定周播开始日）。先行段第 1～N 集在首播日一起放出，第 N+1 集从固定周播日开始每周一集；
  • 逐段核实的排期：数据里有 episodeSchedules 数组（每段写明起止集数、日期、时间、间隔天数），就不再“猜”周播，完全按核实的段展开（intervalDays:0 表示同一天连播多集）。
一句话记忆：eventsForWeek 回答的问题是——“给定本周 7 天，每部番在这 7 天里播了哪些集、显示在哪一天什么时间”。它是纯函数：同样的数据+周起点，永远返回同样的事件列表，所以可以直接写测试（tests/calendar.test.mjs 里全是它的断言）。

5时间轴布局：裁切 + 贪心分道（真的是一道算法题）

桌面端周历是纵向时间轴：节目按时间定位。第一个问题：时间轴从几点画到几点？答案是按当周事件动态裁切，避免大片空白：

lib/calendar.js 第 61～84 行（真实代码，节选）
export function timelineBoundsForEvents(events, defaultStartMinutes, defaultEndMinutes, ...) {
  if (!events.length) return { startMinutes: defaultStartMinutes, endMinutes: defaultEndMinutes };

  const eventMinutes = events.map((event) => timeToMinutes(event.time));
  const visibleEndMinutes = Math.ceil(defaultEndMinutes / 60) * 60;
  const startMinutes = Math.max(
    defaultStartMinutes,
    Math.min(Math.floor(Math.min(...eventMinutes) / 60) * 60, visibleEndMinutes - 60), // 最早节目向下取整到整点
  );
  const endMinutes = Math.max(
    startMinutes + 60,
    Math.min(Math.ceil((Math.max(...eventMinutes) + eventDurationMinutes) / 60) * 60, visibleEndMinutes), // 最晚节目+卡片高后向上取整
  );
  return { startMinutes, endMinutes };
}

这就是几个 floor/ceil + clamp：最早节目向下取整到整点，最晚节目加卡片高度后向上取整，再夹在默认范围内（空周回退 05:00～次日 05:00）。

第二个问题更有意思：同一时间点附近有多个节目，怎么排到不同的“泳道”里不重叠？

lib/calendar.js 第 180～218 行（真实代码，节选）
export function layoutTimelineEvents(events, blockDurationMinutes = TIMELINE_EVENT_DURATION_MINUTES) {
  const sorted = [...events].sort((left, right) => timeToMinutes(left.time) - timeToMinutes(right.time));
  const clusters = [];                    // 第一步：把互相重叠的节目聚成“簇”
  let currentCluster = [];
  let currentClusterEnd = -Infinity;

  for (const event of sorted) {
    const start = timeToMinutes(event.time);
    if (currentCluster.length && start >= currentClusterEnd) {   // 与簇不重叠 → 开新簇
      clusters.push(currentCluster);
      currentCluster = [];
      currentClusterEnd = -Infinity;
    }
    currentCluster.push(event);
    currentClusterEnd = Math.max(currentClusterEnd, start + blockDurationMinutes);
  }
  if (currentCluster.length) clusters.push(currentCluster);

  return clusters.flatMap((cluster) => {
    const laneEnds = [];                  // 第二步：簇内贪心分道
    const positioned = cluster.map((event) => {
      const start = timeToMinutes(event.time);
      let lane = laneEnds.findIndex((end) => end <= start);   // 找第一条空闲泳道
      if (lane === -1) lane = laneEnds.length;                 // 都忙 → 开新泳道
      laneEnds[lane] = start + blockDurationMinutes;
      return { event, lane };
    });
    return positioned.map(({ event, lane }) => ({ event, startMinutes: timeToMinutes(event.time), lane, laneCount: laneEnds.length }));
  });
}

这是一个标准的区间调度 + 贪心：

  • 按开始时间排序；
  • 把互相重叠的区间聚成“簇”（两区间不重叠的条件：后一个开始 ≥ 前一个结束）；
  • 簇内扫描，每个区间放进“最早空闲”的泳道，放不下就新开一条——贪心保证泳道数最优（这是“区间着色”的经典结论，和“活动安排”问题同源）。
竞赛对照：如果你刷过“区间覆盖 / 活动安排 / 任务调度”类贪心题，这段代码就是那类题的直接落地——只不过“区间”是播出时段，泳道是并排的节目卡。看懂它，你对“刷题学的算法在真实项目里长什么样”就有了第一手样本。

6时区换算：把日本时间变成北京时间

历史数据的原料是 JST（UTC+9），网站要显示北京时间（UTC+8）。差 1 小时，但不能靠“小时减 1”硬算——跨天、跨月都要正确。项目交给浏览器内置的时区引擎：

lib/schedule.js 第 1～10、55～72 行（真实代码，节选）
const beijingFormatter = new Intl.DateTimeFormat("en-CA", {
  timeZone: "Asia/Shanghai",   // 用目标时区格式化
  weekday: "short", year: "numeric", month: "2-digit", day: "2-digit",
  hour: "2-digit", minute: "2-digit", hourCycle: "h23",
});

// 把 "2026-07-05" + "23:30"（JST）拼成一个时间点
const airingAt = new Date(`${premiereDateJst}T00:00:00+09:00`);
airingAt.setTime(airingAt.getTime() + (hour * 60 + minute) * 60_000); // +23.5 小时

// 用北京时区把这个时间点“重新念一遍”
const parts = Object.fromEntries(beijingFormatter.formatToParts(airingAt) /* ... */);
return { date: `${parts.year}-${parts.month}-${parts.day}`, weekday: parts.weekday, time: `${parts.hour}:${parts.minute}` };

思路是“先求绝对时间点，再用目标时区格式化”：JST 的 2026-07-05 23:30 = UTC 的 14:30 = 北京时间的 22:30。跨天的情况自动正确（JST 00:30 → 北京前一天 23:30）。这个函数还有大段防御性校验（正则、月份天数），全部在“坏数据进不来”这条原则上。

维护提示：2026 年 7 月番的数据直接来自 YUC 的北京时间排期（premiereDateBeijing/beijingTime 已填），根本不走 JST 换算；只有历史季度（2020～2025）才用 JST 原料换算。两种来源都收敛到同一组字段，下游代码无需区分。

7搜索与已看：规范化 + 集合运算

搜索：规范化后子串匹配

lib/anime-search.js 全文（只有 10 行）
function normalizedTitleText(value) {
  return value.normalize("NFKC").toLowerCase().replace(/\s+/g, ""); // 全角→半角、变小写、删空白
}

export function matchesAnimeTitle({ titleZh, titleJa }, query) {
  const normalizedQuery = normalizedTitleText(query);
  if (!normalizedQuery) return true;   // 空查询 = 匹配全部

  return [titleZh, titleJa].some((title) => normalizedTitleText(title).includes(normalizedQuery));
}

为什么不用 KMP 之类？因为总数据量只有几千条、每条标题几十字，线性子串匹配足够快；真正的难点是“用户输入不规范”——全角半角、大小写、空格。所以先 NFKC 规范化 + 小写 + 去空白 再匹配。这里体现工程上的一个判断：算法复杂度不重要时，先解决输入规范化。

已看标记：单集是原子，集合是模型

lib/anime-episode-views.js 第 1～11、73～91 行（真实代码，节选）
export function episodeViewKey({ animeId, episodeStart, episode }) {
  return animeId + ":" + episodeStart + "-" + episode;   // 稳定键：番剧 ID + 集数
}

export function episodeViewUnitsForRange({ episodeStart, episode }) {
  const units = [];
  for (let currentEpisode = episodeStart; currentEpisode <= episode; currentEpisode += 1) {
    units.push({ episodeStart: currentEpisode, episode: currentEpisode }); // 连播展开成单集
  }
  return units;
}

export function updateEpisodeViews(watchedEpisodes, watchedEpisode, watched) {
  // 全部规范成单集后，用"键集合"做并/差运算
  const normalizedEpisodes = watchedEpisodes.flatMap((candidate) =>
    episodeViewUnitsForRange(candidate).map((unit) => ({ animeId: candidate.animeId, ...unit })));
  const episodeViews = episodeViewUnitsForRange(watchedEpisode).map((unit) => ({ animeId: watchedEpisode.animeId, ...unit }));
  const keys = new Set(episodeViews.map(episodeViewKey));
  if (watched) {
    return normalizedEpisodes.concat(episodeViews.filter((view) =>
      !normalizedEpisodes.some((candidate) => episodeViewKey(candidate) === episodeViewKey(view))));
  }
  return normalizedEpisodes.filter((candidate) => !keys.has(episodeViewKey(candidate)));
}
  • 设计原则：“已看”永远按单集存储（第 3 集就是第 3 集一条记录），日历卡片上“1-3 连播”只是显示上的合并，不影响存储；
  • 数学结构：勾选 = 集合并集（watched=true 时把新单集并入），取消勾选 = 集合差集（watched=false 时从键集合里删掉）；
  • 键的设计：animeId:episodeStart-episode 就是“集合元素的编号”，保证同一集不会重复入库——这正是竞赛里“用字符串拼接当键去重”的标准技巧。

8本章自测

1.（单选）startOfWeek("2026-07-12") 返回什么？（2026-07-12 是周日）

(getUTCDay()+6)%7：周日=0 → (0+6)%7=6，往前退 6 天 = 07-06 周一。这个断言就写在 tests/calendar.test.mjs 第 44 行，可以直接去验证。

2.（单选）一部番数据里写着 beijingTime: "25:00"，它会显示在周历的哪里？

25:00 = 次日 01:00，且 00:00～04:59 的节目归前一天栏目。这是日本深夜动画惯例 + 本项目的固定规则，由 formatBroadcastTime 与 layoutBroadcast 统一处理。数据里写 "24:00"、"25:00" 都是合法的。

3.（多选）layoutTimelineEvents 里用到了哪些算法思想？

没有二分。流程是：排序 → 扫描聚簇（重叠判断：start < 簇结束时刻）→ 簇内找第一条 end ≤ start 的泳道（线性 findIndex），放不下就新开。泳道数很少，O(n·lane) 足够快，不需要更复杂的结构——又是一个“数据规模决定算法选择”的例子。
