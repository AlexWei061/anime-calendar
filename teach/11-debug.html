修 bug 方法论：把它当成一道证明题

修 bug 不是「碰运气多试几次」，而是一套可以复用的推理流程。你打竞赛练出来的三种能力——不慌、会二分、会造数据——在这里全部用得上。这一章教你把「这个页面怎么又坏了」翻译成「我该怎么定位到那一行」。

核心方法论 前置：第 01～09 章 配套：第 10 章维护 SOP 工具：浏览器 DevTools

1心态开场：bug 就是「反例」，你找到了一个

数学上，一个命题「系统总是正确」被一行现象推翻，那个现象就是反例。bug 的定义就是：系统的实际行为 ≠ 你的预期。所以出现 bug 是好事——你拿到了一个反例，它精确地告诉你「某个假设不成立」。

修 bug 和数学证明的节奏完全一样：

  • 先构造反例（复现）——找到能 100% 触发错误的最简操作序列。
  • 再缩小范围（二分）——把「可疑代码」一分为二，判断 bug 在哪半边。
  • 最后定位到破坏不变量（invariant）的那一行——所谓 invariant，就是「任何时候都必须成立的性质」，比如 catalogCount === anime.length、比如「先行集数不能塞进电视时段」。bug 的本质，就是某一行代码破坏了一个你原本以为成立的不变量。
给竞赛选手：你在考场上已经会「造一组卡掉自己代码的数据 → 二分出错的区间 → 盯着那行找边界」。修 bug 一模一样，只是「数据」换成了「操作步骤」，「printf 大法」换成了 console.log，「gdb 单步」换成了浏览器 Sources 断点。唯一的新东西是 Web 报错的红字格式，下面第 3 节专门教你读。
反例 counterexample
能让系统行为与预期不一致的最小操作序列。修 bug 第一步永远是先「拿到一个稳定的反例」。
不变量 invariant
程序任何时刻都必须成立的性质。bug = 某一行破坏了某个不变量；修 bug = 找到并恢复那个不变量。
调用栈 stack trace
报错时记录下的「谁调用了谁」的函数调用链，从最外层调用到出错的那一行。
回归测试 regression test
专门为「某个 bug 不能再出现」而写的测试。它先失败、修复后变绿，从此一直帮你盯这个坑。

2五步法：从「它坏了」到「修好了」

  1. 稳定复现：找到能 100% 触发 bug 的最简操作序列（最小反例）。「偶尔点一下会闪」不算复现——你要的是「第 1 步点 X，第 2 步点 Y，必现」。
  2. 缩小范围：二分法。注释掉一半代码、或只留一半数据，看 bug 还在不在——和竞赛里二分定位错误区间一模一样，每步排除一半嫌疑。
  3. 定位：读报错（第 3 节）、console.log 打印中间值、Sources 打断点单步、Network 看请求，找到破坏不变量那一行。
  4. 最小修复：只改必要的那一处，不顺手重构。能改一行就不改两行。
  5. 回归：写/改一条测试，断言「这个 bug 不能再回来」，然后再跑全量测试。
记忆锚点：复现 → 二分 → 定位 → 最小修复 → 回归。前两步是「缩小嫌疑」，第三步是「锁定凶手」，第四步是「动刀」，第五步是「装监控防止再犯」。跳过回归，同一个坑你迟早掉第二次。

五步法实战：追番保存后偶尔全丢

拿本项目一个真实陷阱走一遍。症状：用户收藏了很多番，点保存后偶尔整张追番列表变空。

  1. 稳定复现：发现「收藏超过 50 部」时才触发——50 部以内没事，超过 50 部偶发清空。
  2. 缩小范围：定位到写接口 app/api/anime-selections/route.ts 的 PUT，是「保存」这条路出问题。
  3. 定位：读代码——D1 单条语句最多绑定 100 个参数，每个追番写入绑 2 个参数（邮箱 + 番剧 ID），所以插入必须按最多 50 个 ID 分批。如果「删旧列表」和「各插入批次」不在同一次 db.batch() 里，大列表某批插入失败就会先清空、后失败，留下空列表。
  4. 最小修复：把删除 + 所有插入批次放进同一次 db.batch()，保持原子替换。
  5. 回归：写测试断言「大列表保存失败不会清空原有追番」。

修复后的真实代码长这样——注意「删除」和「所有插入批次」被包在同一个 db.batch([...]) 里：

app/api/anime-selections/route.ts PUT 的原子替换（真实代码）
const db = await getDb();
await db.batch([
  db.delete(animeSelections).where(eq(animeSelections.userEmail, user.email)),
  ...selectionInsertBatches(animeIds).map((batch: string[]) =>
    db.insert(animeSelections).values(batch.map((animeId) => ({ userEmail: user.email, animeId }))),
  ),
]);

配套的分批函数在 lib/anime-selections.js——每 50 个 ID 切一批：

lib/anime-selections.js selectionInsertBatches（真实代码）
export function selectionInsertBatches(animeIds) {
  return Array.from({ length: Math.ceil(animeIds.length / 50) }, (_, index) =>
    animeIds.slice(index * 50, (index + 1) * 50),
  );
}

3阅读报错三件套：类型 → 信息 → 调用栈

浏览器控制台（或终端）的红字不是玄学，它按「三件套」组织，从外到里读：

  1. 错误类型：告诉你「错的是哪一类」。四种最常见：SyntaxError（语法写错了，像 C++ 少个分号）、TypeError（对错误类型做了操作，像对 int 调成员）、ReferenceError（用了没定义的变量）、RangeError（数值越界，像数组越界/时间格式非法）。
  2. 错误信息 error.message：黄金线索。例如 TypeError: Cannot read properties of null (reading 'beijingTime') 直接告诉你「某个东西是 null，你却读了它的 beijingTime」。
  3. 调用栈 stack trace：一条函数调用链，像递归展开的「谁调用了谁」。从上往下读，第一处「你自己项目里的文件」就是嫌疑现场；框架内部帧（react-dom、next 那些）跳过不看。
错误类型含义本项目里典型场景
SyntaxError代码语法不合法，解析就失败改 data/anime.js 漏了逗号/括号
TypeError对值做了它不支持的操作null/undefined 上读字段、把字符串当函数调
ReferenceError引用了一个不存在的标识符拼错了导入名、用了未声明变量
RangeError数值超出合法范围lib/calendar.js 的 timeToMinutes 遇到非法时间格式

拿 RangeError 举例，lib/calendar.js 里真的会主动抛它——时间格式不是 HH:MM 或分钟超过 59 就报：

lib/calendar.js timeToMinutes（真实代码，省略无关行）
function timeToMinutes(time) {
  const match = /^(\d{2}):(\d{2})$/.exec(time);
  if (!match) throw new RangeError("Invalid schedule time: " + time);

  const [, hour, minute] = match.map(Number);
  if (minute > 59) throw new RangeError("Invalid schedule time: " + time);
  return hour * 60 + minute;
}
类比：错误类型像评测机的 CE / RE / WA，error.message 像「第几组数据错了」，stack trace 像「错误发生在你代码的哪一行」——三者合起来，就是一份自动写好的 debug 报告，先读它，别急着瞎改。

4DevTools 四面板实操（按 F12 打开）

① Console

控制台 = 你的 printf

console.log(x) 打印值、点开对象展开看结构、还能直接输入表达式当 REPL 用（像 Python 交互式解释器）。查「这个变量此刻到底是什么」最快的地方。

② Sources

断点 = 你的 gdb

点行号打断点，代码跑到这里停住；再「Step over（跳过这一行）/ Step into（钻进函数里）」，右侧看局部变量。和你 IDE 里单步调试 C++ 一模一样。

③ Network

网络 = 看消息怎么传

每个请求一条记录：状态码（200 成功 / 401 未登录 / 500 服务器错）、请求与响应头、Preview 看返回的 JSON，还有 cookies 栏。

④ Application

存储 = 看状态记在哪

查 localStorage 里的 ac-theme（主题偏好），查 Cookie 里的 ac_session（登录会话）。「我没登录吗？」「主题怎么没存住？」都来这里看。

四个面板各管一段链路，配合着用：

  • Console：适合看「纯函数」对不对。比如直接在控制台里 import lib/calendar.js 的 formatBroadcastTime，输入 "25:00"，看是不是输出 "次日 01:00"——这就是用 REPL 单测一个函数。
  • Sources：适合「逻辑对但结果不对」的情况。在 lib/calendar.js 的 layoutBroadcast 里打断点，单步看 minutes 和 date 怎么变。
  • Network：适合「请求没走对」。点开一个 /api/... 请求，看状态码是 401（没登录）还是 500（服务器报错），再看 Preview 里服务器返回的 JSON 错误信息。
  • Application：适合「状态丢了」。登录后这里应该能看到 ac_session Cookie、ac-theme localStorage 条目。
项目专属的两个键：ac-theme（localStorage，存亮/暗主题选择）、ac_session（Cookie，登录会话）。排查「主题没记住」「一直提示未登录」时，先到 Application 面板确认这两个值在不在、有没有过期。

搜索匹配是「规范化后子串包含」——两边必须先走同一套 NFKC + 小写 + 去空格：

lib/anime-search.js 标题规范化（真实代码）
function normalizedTitleText(value) {
  return value.normalize("NFKC").toLowerCase().replace(/\s+/g, "");
}

export function matchesAnimeTitle({ titleZh, titleJa }, query) {
  const normalizedQuery = normalizedTitleText(query);
  if (!normalizedQuery) return true;

  return [titleZh, titleJa].some((title) => normalizedTitleText(title).includes(normalizedQuery));
}
用法：这张表是「常见病」索引，不是「万能药」。遇到没在表里的症状，回到第 2 节的五步法一步步走——表只能加速常见情况，方法论才覆盖所有情况。

6回归测试示范：先写「会失败的断言」，再修

AGENTS.md 的原文要求是：「改 bug 先在对应的 tests/*.test.mjs 添加能失败的回归测试，再做最小修复」。这跟「先写一组能卡掉 bug 的测试数据，再改代码直到通过」是一个思路：先让 bug 变成一条红掉的测试，修完它变绿，这条测试就永远帮你盯着。

下面这条是 tests/calendar.test.mjs 里真实存在的测试——「先行多集首播」的场景：

tests/calendar.test.mjs 先行多集首播的回归测试（真实代码）
test("keeps the full episode range for a multi-episode premiere", () => {
  const multiEpisodePremiere = { ...weeklyShow, premiereEpisodeCount: 3 };

  assert.deepEqual(
    eventsForWeek([multiEpisodePremiere], "2026-06-29").map(({ episodeStart, episode, date }) => ({ episodeStart, episode, date })),
    [{ episodeStart: 1, episode: 3, date: "2026-07-01" }],
  );
  assert.deepEqual(
    eventsForWeek([multiEpisodePremiere], "2026-07-06").map(({ episodeStart, episode, date }) => ({ episodeStart, episode, date })),
    [{ episodeStart: 4, episode: 4, date: "2026-07-08" }],
  );
});

这条测试断言了两件事：首播那一周，7 月 1 日当天把第 1～3 集一起显示成一张卡（episodeStart: 1, episode: 3）；下一周，固定周播从第 4 集开始（episodeStart: 4, episode: 4）。

本项目一条硬性回归要求：凡是涉及「先行多集 + 后续周播」的排期，回归测试必须同时断言——① 先行日显示正确的集数范围、且没有虚构时刻；② 首个固定周播日从下一集开始。写测试时这三条缺一不可，别只测「首播日」而漏了「下一集从哪开始」。

同样的要求在数据层也有一道真实回归测试兜底——tests/anime-data.test.mjs 里《无职转生 第3期》的「双集先行 + 周日周播」用例：

tests/anime-data.test.mjs 无职转生双集首播回归测试（真实代码，省略无关行）
const mushoku = anime.find(({ id }) => id === "mushoku-3");

它断言：首播周显示「第 1～2 集」一张卡，下一周固定周日周播从「第 3 集」开始。算法层（tests/calendar.test.mjs）和数据层（tests/anime-data.test.mjs）各守一道关——你改哪一层，都逃不掉这组先行+周播断言。

7求助技巧：别空手问问题

自己卡住超过一段时间，就求助。但「它坏了」不是一个问题——好的求助像一份最小可复现的报告，别人（或 AI、或搜索引擎）一看就能接手：

  • 报错全文：错误类型 + error.message + stack trace，原样贴，别只截「后半句」。
  • 最小复现：一句「在第 X 步点 Y 之后必现」+ 相关代码片段。
  • 你已尝试的操作：改过什么、跑过什么、结果如何——避免对方重复你已经排除的方向。

对比一下两种问法：

差的求助好的求助
「追番保存之后列表没了，怎么办？」「收藏 60 部番后点保存，追番列表偶发变空；50 部以内正常。报错 Unable to save anime selections，我已经确认 app/api/anime-selections/route.ts 的 PUT 走了 500 分支。」
橡皮鸭调试法：把问题用完整句子讲给一只橡皮鸭听，讲到一半常常自己就明白了。因为「把问题说清楚」这个动作，逼你重新梳理所有假设，bug 往往就藏在某个你「想当然」的假设里。所以哪怕没人听，也先把问题写下来。
别忘了项目自带的历史决策：遇到「为什么要这么设计」的疑问，先翻 docs/superpowers/——里面是历史设计和实施计划，能解释很多「看起来奇怪但其实是刻意的」决定。别一上来就把它当 bug 改掉。

8本章测验

1.（单选）修 bug 五步法的正确顺序是？

先拿到「必现的最简反例」（复现），才能二分缩小；缩到嫌疑最小范围后再定位那一行，做最小修复，最后写回归测试防复发。顺序颠倒（比如没复现就急着修）就像没造出卡掉代码的数据就瞎改算法。

2.（多选）以下哪些是「定位 bug」的合法手段？

console.log、断点单步、Network 看请求、二分注释，都是「缩小+定位」的正规手段。而「整段删掉报错代码」是绕过不是定位——删掉可能让别的功能一起坏，bug 本身还在。定位是「找到破坏不变量那一行」，不是「让红字消失」。

3.（单选）读 stack trace（调用栈）时，正确的姿势是？

调用栈是「谁调用了谁」的链，最上面通常是你代码离得最近的调用点。正确的读法：从上往下，第一处指向你项目文件（如 lib/calendar.js）的帧就是嫌疑现场；react-dom、next 这些框架内部帧跳过。只看最后一行会漏掉真正出错的位置。
